## 1. 핵심 판단

현재 화면의 작품은 **legacy 작품 테이블을 가져온 결과**다. `crawler/collections.py`의 제목 분석기는 **미리보기 전용**이고, 새 글 수집 후 작품을 생성·갱신하는 실행 경로에는 연결되어 있지 않다. 따라서 화면의 잘못된 묶음을 이 분석기 탓으로 단정하거나, 분석기를 교체하면 화면도 고쳐진다고 생각하면 안 된다.

가장 먼저 다룰 문제는 다음과 같다.

1. 기존 목차와 새 글 사이의 갱신 경로 부재. 새 글을 수집·게시해도 작품 소속과 목차가 자동 확장되지 않는다.
2. 최근 읽기 기록 500건 제한이 완독 기록까지 지워 장편의 진행 상태를 보존하지 못하는 문제.
3. 작품 종류·원래 회차·묶음 근거가 부족해 단편/연재, 분할 회차, 외전, 동명 작품을 정확히 표현하기 어려운 구조.
4. 새 분석기의 과도한 제외와 일부 오분류. 현재 규칙만으로 legacy를 일괄 대체하면 대량 누락이 생긴다.
5. 목록·홈·상세가 읽기 상태와 이어 읽을 편을 서로 다르게 계산하는 문제.

권장 방향은 기존 SQLite와 정적 summary/detail/membership 구조를 유지하면서, **근거를 남기는 보수적 후보 생성 → 충돌 격리 → 변경 비교 → 원자적 적용**을 추가하는 것이다. 전체 제목 fuzzy clustering, 임베딩 검색, LLM 판정을 바로 도입할 필요는 없다.

## 2. 실제 데이터 흐름과 유지할 장점

| 단계 | 현재 동작 | 근거 |
|---|---|---|
| 기존 작품 적재 | legacy `collections`의 ID·제목·종류를 복사하고 `collection_episodes`를 순서대로 변환 | `scripts/import_legacy_auxiliary.py:165`, `:192`, `:213` |
| 새 글 수집 | 발견·본문·버전·수집 결과를 저장. 작품 테이블 갱신 호출 없음 | `crawler/archive_pipeline.py:44`, `crawler/store.py:70`, `:120` |
| 후보 분석 | 제목을 정규화하고 명시적 회차가 있는 동일 게시판·동일 base만 묶음 | `crawler/collections.py:62`, `:103` |
| 후보 실행 | DB를 읽고 후보 통계·큰 묶음 50개를 출력. 작품 테이블 쓰기 없음 | `scripts/preview_collections.py:12` |
| 정적 게시 | 저장된 작품을 summary, ID % 64 detail shard, 게시판별 membership으로 출력 | `scripts/export_static.py:1420`, `:1575` |
| 목록 | 전체 summary를 필터·정렬한 뒤 100개씩 표시 | `edge/public/app.js:1426`, `:1532` |
| 상세·연속 읽기 | 필요한 detail shard와 membership을 지연 로드. 보존 객체 없는 편은 건너뜀 | `edge/public/app.js:1767`, `:1796`, `:2163` |

유지할 장점:

- 원본 글 정체성은 `board_id:external_post_id`다. 본문 해시가 바뀌어도 읽기 기록을 연결할 수 있다.
- 후보 결과는 입력 순서와 무관하게 결정적이며 NFKC·공백·대소문자 정규화가 있다.
- 요약과 상세가 분리되어 목록 진입 때 모든 목차를 받지 않는다. 100개 표시는 결과 절단이 아니라 `더 보기` 페이지 단위다.
- 게시 검증은 중복 소속, summary/detail 불일치, 존재하지 않는 본문 참조 등을 검사한다. 실패한 detail/membership promise는 제거해 재시도를 허용한다.
- 누락 글의 자리와 원본 ID를 보존한다. 수집 실패 때문에 뒤 회차가 앞으로 당겨져 원래 연결이 사라지는 것보다 낫다.

## 4. 확인된 문제와 개선 우선순위

P1은 데이터 손실·목차 최신성·읽기 상태 정확성, P2는 품질·안정성·검색 편의, P3는 측정 후 개선이다. 운영 장애 발생 여부와 별개로 코드나 재현에서 확인한 문제를 표시했다.

### F01. P1 — 수집과 작품 갱신이 연결되지 않음 [코드 확인]

- 근거: `crawler/collections.py:103`, `scripts/preview_collections.py:12`, `crawler/archive_pipeline.py:44`, `crawler/store.py:120`, `scripts/import_legacy_auxiliary.py:192`.
- `preview_collections` 호출자는 preview 스크립트와 테스트다. 저장소의 작품 INSERT 경로는 legacy import와 테스트이며 일반 수집 경로에 없다.
- 영향: 신규 회차·새 작품·제목 수정이 글 검색에는 나타나도 작품 목차와 편수에는 자동 반영되지 않는다. export를 다시 해도 테이블에 없는 소속을 만들지 않는다.
- 개선: 수집 성공 후 변경된 제목·게시판·원본 ID를 대상으로 후보를 다시 계산하는 별도 단계와 적용 명령을 둔다. 첫 도입은 전체 dry-run과 변경표만 만들고, 검증된 규칙에 한해 갱신을 활성화한다. 본문 HTML만 달라진 글은 그룹 재계산 대상에서 제외할 수 있다.
- 검증: 기존 1·2화에 3화가 추가될 때 같은 collection ID에 한 번만 붙는지, 재실행·중단 복구에도 중복이 없는지 확인한다.

### F02. P1 — 최근 기록 500건 제한으로 완독·스크롤 기록도 삭제됨 [실행 재현]

- 근거: `edge/public/app.js:2039`의 `rememberHistory`, `:173`의 `persistUserState`, `:1543`의 `collectionReadingProgress`.
- `historyEntries.slice(0, 500)`으로 잘라낸 배열에서 영구 저장용 history와 scroll을 다시 만든다. 최근 목록에서만 숨기는 제한이 아니다.
- 실제 함수를 추출해 실행: 완독 500건 후 새 글을 열면 완독 기록은 499건만 남았다.
- 영향: 여러 작품을 오가면 이전 완독이 풀리고, 실제 896편 작품은 이 상태 모델로 전체 896편 완독을 유지할 수 없다. 로컬 보존본에 500편 초과 작품이 9개 존재한다.
- 개선: 최근 목록의 표시 제한과 지속되는 글별 progress를 분리한다. 우선 기존 user-state의 글별 기록을 보존하고 화면만 제한한다. 저장량 측정 뒤 필요할 때 IndexedDB 등 저장소 변경을 검토한다. 작품별 최대 회차 하나만 저장하면 건너뛰기·외전·재독을 잃으므로 대안이 아니다.
- 검증: 501건과 896편 완독 후 저장·새로고침·내보내기·가져오기에도 앞쪽 progress가 유지되어야 한다. 이미 잘린 기록은 사전 백업 없이는 자동 복구할 수 없다.

### F03. P1 — 목록은 보존 불가 편의 완독 기록까지 분자에 포함 [실행 재현]

- 근거: `edge/public/app.js:1543`, `:1580`, `:1613`; `edge/public/reading-model.js:70`.
- summary의 분모는 `entry_count - unavailable_count`지만 membership을 순회하는 목록 계산은 해당 편의 보존 가능 여부를 모른다. 상세는 available entry만 세므로 서로 다르다.
- 재현: 총 3편에서 제2편만 현재 보존 불가, history에는 제2·3편 완독, 제1편은 미독인 경우 목록은 `2/2 다 읽음`, 상세는 `1/2`다. 실제 `collectionReadingProgress`를 추출해 실행했다.
- 개선: membership에 읽기 가능 정보를 제공하거나 unavailable 글의 stable ID를 별도로 전달해 동일 집합으로 분자·분모를 계산한다. 단순히 분자를 분모 이하로 clamp해도 잘못된 완독 판정은 해결되지 않는다.
- 검증: 읽었던 글이 다음 release에서 unavailable이 된 경우, 처음부터 missing인 경우, 다시 보존 가능해진 경우 모두 목록과 상세가 일치해야 한다.

### F04. P2 — 상세 요청 순서가 사용자 선택 순서를 보장하지 않음 [코드상 경쟁 조건]

- 근거: `edge/public/app.js:1589`의 `openCollectionDetail`; 대비되는 목록 request ID 가드 `:1427`, 본문 abort `:1873` 부근.
- 상세 함수는 await 이후 현재 요청인지 확인하지 않고 화면과 URL을 갱신한다. A 선택 → B 선택 → B 응답 → A 응답이면 오래된 A가 마지막 화면을 차지할 수 있다. 상세 요청 중 본문을 열어도 같은 종류의 경쟁이 가능하다.
- 개선: 작품 상세·본문을 포함한 Reader 선택 세대 번호를 공유하고, 응답 반영·오류 표시·busy 해제 전에 최신 선택인지 확인한다. 공유 shard fetch를 무조건 취소하는 방식보다 표시 권한을 가드하는 것이 단순하다.
- 검증: 서로 다른 shard의 응답 순서를 의도적으로 뒤집는 E2E와 목차 요청 중 본문 이동을 추가한다. 이번 검토에서는 브라우저 지연 재현까지 실행하지 않았다.

### F05. P2 — 읽는 중 상태와 이어 읽기 종료 상태의 의미 충돌 [실행 재현·기존 정책 확인]

- 근거: `edge/public/reading-model.js:39`, `:70`; `edge/public/app.js:1625`; `docs/15_reader_navigation_refresh.md:329`; `edge/e2e/viewer.spec.js:1071`.
- 마지막 편만 완독하고 앞쪽을 건너뛰면 `collectionContinueTarget`은 `finished`, `collectionOccupancy`는 `reading`이다. 목록에는 ‘읽는 중/이어 읽기’가 보이지만 상세 이어 읽기 버튼은 숨겨진다.
- 앞쪽 미독으로 자동 되돌아가지 않는 정책 자체는 기존 문서·테스트에 명시되어 있다. 이를 무조건 첫 미독으로 되돌리는 버그 수정은 정책을 깨뜨린다.
- 개선: `다음 편 없음/마지막 편 도달`과 `모든 보존 가능 편 완독`을 구분한다. `앞쪽 미독 N편 보기`를 별도 행동으로 제공하고 자동 이어 읽기 정책은 유지한다.
- 추가: 전편 unavailable 또는 0편인 경우 `collectionRowCopy`는 ‘시작하기’를 반환한다. 2/2편 unavailable 입력으로 재현했다. 읽을 수 없는 작품은 ‘목차 보기/본문 없음’으로 표시한다.

### F06. P2 — 홈·목록의 이어 읽을 회차가 실제 상세와 다를 수 있음 [코드 확인]

- 근거: `edge/public/app.js:534`, `:557`, `:1494`; `edge/public/reading-model.js:48`.
- 목록은 읽는 중인 편이 하나라도 있으면 가장 최근에 연 `lastPosition`을 재개 위치로 추정한다. 최근 5화는 완독, 이전 2화는 읽는 중이면 목록은 5편, 상세는 2편을 가리킬 수 있다.
- 홈은 다음 편을 `lastPosition + 1`로 추정한다. 바로 다음 위치가 보존 불가이면 실제 이동 대상과 다른 숫자를 보여준다.
- 개선: 정확한 target을 모르는 summary 행은 우선 ‘이어 읽기’만 표시한다. 회차 숫자가 필요하면 상위 홈 3작품 등 필요한 대상에만 실제 목차 계산을 적용하거나 정확한 가용 순서 정보를 제공한다. 모든 상세 shard를 선로딩하지 않는다.

### F07. P2 — 선택한 목록과 무관한 membership 실패가 전체 목록을 막음 [코드 확인]

- 근거: `edge/public/app.js:1437`, `:1573`, `:1580`.
- 읽기 상태 필터가 ‘전체’여도 history의 모든 게시판 membership을 `Promise.all`로 기다린다. 이 중 하나가 실패하면 현재 게시판 작품 목록도 오류 처리된다.
- 개선: 후보 게시판을 먼저 좁히고 관련 진행 상태만 구한다. ‘전체’ 목록은 제목·편수부터 표시하고 진행 상태 실패를 해당 정보에 국한한다. 읽기 상태 필터에서는 미확인을 ‘안 읽음’으로 간주하지 말고 재시도·미확인을 표시한다.
- 검증: 다른 게시판 membership만 500/404로 실패시켰을 때 현재 목록은 열리고, 잘못된 읽기 상태로 필터링되지 않아야 한다.

### F08. P2 — 검색과 작품이 서로 다른 release를 사용할 수 있음 [조건부 코드 위험]

- 근거: `edge/public/search-worker.js:19`, `edge/public/app.js:1697`, `:1759`.
- 검색 Worker와 작품 index가 각각 `/archive/release.json`을 가져와 별도로 캐시한다. 탭을 켠 채 게시가 이루어지고 이후 처음 작품을 열면 서로 다른 시점의 데이터가 함께 사용될 수 있다.
- 영향: 제목·게시판 metadata·글 존재 여부·작품 소속의 기준이 어긋날 수 있다. 각 immutable 객체 자체가 잘못되었다는 뜻은 아니다.
- 개선: 한 세션의 manifest 또는 release 식별자를 공유한다. 새 release 전환 시 summary/detail/membership/search를 같은 기준으로 전환하거나 새로고침을 안내한다. 원격 발생 여부는 미확인이다.

## 6. 권장 생성·갱신 알고리즘

### 6.1 순서

1. **원문을 유지하며 구조 추출**: 원래 제목, 정규화 base, 시즌/부/장/회차/분할, 범위, 본편·외전·막간 종류, 상태 태그, 해석 규칙을 분리한다. 인식 못한 부분은 삭제하지 않는다.
2. **좁은 후보군 생성**: 우선 게시판 + 정확한 base로 찾는다. 창작 게시자 일치, 원본 목차 링크, 번역 원문 URL, 연속 회차를 보조 근거로 쓴다. 번역자 변경은 흔하므로 author 불일치를 모든 게시판에서 절대 분리 조건으로 쓰지 않는다.
3. **충돌 검사**: 동일 번호의 별도 글, 구간 겹침, 본편/외전 종류, 시즌 번호 재시작, 재연재·리메이크, 서로 다른 게시판의 판본을 확인한다. 날짜나 post ID 근접성만으로 같은 작품을 확정하지 않는다.
4. **승인·보류·제외와 이유 기록**: 높은 근거의 신규 연결만 승인하고, 애매한 글과 충돌은 보류한다. 근거 없는 confidence 소수점 대신 rule ID와 판정 사유부터 둔다.
5. **기존 상태와 비교**: 추가·분리·병합·순서 변경·제목 변경·소속 제거를 stable post ID 기준으로 보여준다. 이미 확정된 목차를 미인식 때문에 지우지 않는다.
6. **한 transaction으로 적용**: 충돌 검증 후 작품·소속·요약을 일관되게 갱신한다. 중단·재실행에 멱등적이어야 하며 적용 결과와 알고리즘 버전을 남긴다.
7. **기존 정적 export 검증 재사용**: membership 단일성, summary/detail 일치, 위치 연속성, 본문 객체 참조를 검증하고 게시한다.

기본 exact-base 방식은 유지해도 된다. 파서의 계층·특별편·범위 해석과 충돌 처리부터 개선하는 편이 검증하기 쉽다. 정확도 표본에서 남는 누락이 확인된 뒤에만 제한된 후보군 내부의 문자열 유사도를 검토용 후보 생성에 사용한다. 유사도 연결을 연쇄적으로 합치면 A≈B, B≈C만으로 A와 C까지 오병합할 수 있어 자동 병합 기준으로 쓰지 않는다.

### 6.2 회차 순서와 누락

- `position`은 목차 표시 순번이고 원래 `12화`, `12화 (2)`, `上`, `외전 3`과 다르다. 두 값을 함께 보존한다.
- 시즌 → 부/권 → 본편 회차 → 분할 회차처럼 확인된 계층을 사용한다. 프롤로그·에필로그도 전체 작품 기준인지 특정 부 기준인지 구분한다.
- 막간은 원본 목차·이전/다음 링크·명시된 소속 회차가 있으면 그 위치에 둔다. 불명확하면 시간순 참고 또는 별도 섹션으로 두고 ‘순서 미확인’으로 표시한다.
- 회차 숫자의 공백은 ‘누락 의심’이다. 합본, 0화, 외전, 게시자 번호 오기일 수 있으므로 자동으로 존재하지 않는 글을 생성하지 않는다.
- 원본 ID가 확인된 글의 미보존과, 번호만 비어 있는 의심 회차를 구분한다. 현재 unavailable 수는 목차에 이미 존재하는 글의 상태이며 작품 전체의 완전성을 증명하지 않는다.
- 게시물 175건과 원작 175화는 다르다. 합본·분할이 있으면 목록은 ‘글 175개’, 상세는 원래 회차도 함께 표시하는 편이 정확하다.

### 6.3 작품 정체성·병합·수동 보정

- collection ID는 제목 정규화 결과나 정렬 순번으로 매번 새로 발급하지 않는다. 기존 `/collections/:id` 링크를 보존한다.
- 제목 변경은 표시명·별칭 변경으로 처리한다. 병합된 이전 ID는 새 ID로 연결하고, 분리된 ID는 임의 한 작품으로 보내기보다 분리된 목차를 안내한다.
- 수동 보정은 `같은 작품`, `다른 작품`, `이 글 제외`, `순서 고정`처럼 최소한의 명시적 override로 남겨 재계산에 덮이지 않게 한다.
- 처음에는 작은 검토 JSON/SQLite override와 dry-run 명령이면 충분하다. 별도 관리 웹앱·작업 큐 서비스까지 동시에 만들 필요는 없다.
- 게시판 이동·번역자 변경·리메이크는 우선 작품 간 관련 링크로 표현한다. 실제로 여러 게시판 글을 한 목차에 넣으려면 현재 `entry.board_id === collection.board_id` 검증(`app.js:1690`), 게시판별 membership export(`export_static.py:1539`), 필터 모델을 함께 바꿔야 한다. DB에서 병합만 하면 Reader가 거부할 수 있다.

스키마 관련 주의점:

- `crawler/archive.py:142`의 `UNIQUE(board_id, title)`은 같은 게시판의 동명 별개 작품을 표현하지 못한다. 향후 생성기를 넣을 때 제목 자체를 identity로 쓰지 않고 기존 ID 중심으로 전환해야 한다.
- `collection_entries`는 `(collection_id, post_id)`만 unique라 같은 글을 다른 작품에 넣을 수 있다. 반면 v2 membership은 글당 한 작품이고 exporter도 다중 소속을 거부한다(`scripts/export_static.py:1144`, `app.js:1808`). 의도한 단일 ‘주 목차’를 DB/적용 단계에서 먼저 보장한다. 테마별 모음·추천 목록을 원한다면 주 목차 소속과 다른 관계로 두어 이 제약과 충돌시키지 않는다.
- nullable post_id·source ID를 사용할 경우 실질 정체성의 중복도 검증해야 한다. 기존 UNIQUE만으로 모두 막힌다고 가정하지 않는다.
- `kind`는 DB에서 자유 문자열이고 Reader는 `oneshot` 외 값을 연재로 표시한다. 허용값 검증과 미상 표시가 필요하다. ‘미상’을 추가할 때 DB·export·viewer를 함께 맞춘다.
- 성능 인덱스는 쿼리를 정한 뒤 `EXPLAIN QUERY PLAN`으로 확인한다. `(collection_id, position)` PK는 이미 있으며 같은 인덱스를 다시 추가하지 않는다. 향후 변경 글의 소속 조회에 필요한 `post_id` 선두 인덱스, 정규화 base 후보 조회에 필요한 복합 인덱스는 실제 조회 패턴과 기존 인덱스를 확인한 뒤 추가한다.

## 8. 화면·사용 편의성 검토

### 8.1 제공 화면과 현재 작업 트리의 차이

화면에는 종류 칩과 ‘전체 종류’ select가 동시에 있다. 최초 조사 시 작업 트리에서는 `.collection-kind-field`가 HTML `hidden`이며 `[hidden] { display: none !important; }`가 적용되어 칩만 보이도록 되어 있었다(`edge/public/index.html:130`, `edge/public/app.css:73`). 마지막 diff 대조에서는 `updateDestinationLayout`이 둘러보기에서는 칩, 검색에서는 select를 보이도록 추가 변경되었다. 따라서 **중복 필터는 화면에서 관찰했지만 현재 코드에 그대로 남은 버그라고 기록하지 않는다.** 배포 버전·오래된 페이지 여부는 미확인이다. 작품 기본 정렬도 검토 중 ‘가나다순’에서 ‘최근 글순’으로 변경되었으며, 위 정렬 제안은 사용자가 가나다순을 선택했을 때의 개선이다.

‘132개 작품 중 100개’ 자체는 누락이 아니다. `RESULT_PAGE_SIZE=100`과 `더 보기`가 구현되어 있다(`app.js:67`, `:1182`, `:1190`). 다만 긴 내부 스크롤 하단에만 버튼이 있으면 나머지 작품이 있다는 사실을 놓치기 쉽다.

## 9. 기타 — 함께 확인한 개선·고도화 요소

### O01. 작품 본문이 아닌 게시판도 작품 수에 포함 [로컬 데이터 확인]

`write_intro` 작품소개 361개, `write_intro_19` 19금 작품소개 11개, `write_nirvana` 창작잡담 44개가 작품 테이블에 있다. 내용 확인 없이 개별 그룹을 오분류라고 확정할 수는 없지만, ‘작품 둘러보기’를 실제 읽을 본문 목록으로 이해하면 혼란스럽다.

`app.js:1435`는 작품 존재 여부로 게시판 선택지를 만들 뿐 콘텐츠 역할을 구분하지 않는다. 소개·잡담을 삭제하기보다 본문/소개/자료라는 역할을 지정하고 기본 필터·보조 링크로 구분하는 것이 안전하다. 완결 게시판 역시 모든 개별 작품의 완결 근거를 자동 증명하는 것은 아니다.

### O02. incremental export도 작품 전체를 여러 번 훑음 [코드 확인, 병목 미측정]

`scripts/export_static.py:1433`에서 작품별 가용 수 조회, `:1482`에서 다시 작품별 상세 조회, `:1539`에서 membership 조회를 수행한다. incremental 경로도 `:1998`에서 같은 staging을 호출한다. 로컬 18,369작품 기준 앞의 두 루프만으로 약 36,738번의 entry SELECT가 발생한다.

SQLite 내부 조회이므로 네트워크 N+1과 같은 비용으로 단정할 수 없다. 먼저 collection staging 시간·읽은 행 수·변경된 shard 수를 측정한다. 비용이 유의미하면 한 ordered scan에서 가용 수와 detail을 함께 만들거나 기존 export ledger를 이용해 영향 shard만 다시 만든다. 전체를 Python 메모리에 적재하는 방식은 기존 bounded export의 목적과 충돌하므로 피한다.

### O03. ‘더 보기’마다 정렬·진행 집계·이미 보인 DOM을 다시 생성 [코드 확인]

`app.js:1426`은 매번 전체 summary를 필터·정렬하고 `:1532`는 기존 목록을 비운 뒤 누적 행 전체를 다시 만든다. 현재 규모에서 지연은 측정하지 않았다. 검색 조건·읽기 상태 revision이 같으면 정렬 결과를 재사용하고 새 100행만 붙이는 개선을 측정 후 검토한다. 별도 검색 서버나 가상 스크롤 도입부터 시작할 필요는 없다.

### O04. 스크롤 진행률이 작품 완독의 근거로 완전하지 않음 [코드 확인]

`app.js:2062`, `:2093`은 Reader pane의 전체 scrollHeight 기준이다. 짧아서 스크롤이 없는 글은 0으로 계산되고, 댓글·이미지·레이아웃 변화가 진행률에 영향을 줄 수 있다. 끝의 다음 버튼은 `markCurrentFinished`로 보정하지만 항상 그 버튼을 쓰는 것은 아니다.

본문 끝의 명확한 기준과 사용자의 완독 지정 기능을 검토한다. 화면에 들어왔다고 바로 완독하는 방식은 오히려 오판정을 늘린다. 자동 판정 개선 전에도 수동 보정은 유용하다.

### O05. 원래 회차 정보와 생성 근거가 import에서 축약됨 [코드 확인]

`scripts/import_legacy_auxiliary.py:213`은 `COALESCE(episode_number, id)`로 정렬한 뒤 1부터 position을 새로 매긴다. episode_number 자체와 그 순서의 근거는 canonical entry에 저장하지 않는다. 회차가 없는 글은 다른 글의 회차 숫자와 legacy 행 ID를 한 축에서 비교하므로 올바른 위치인지 추가 검증이 필요하다.

다음 재색인에서는 원본 순서·원래 회차·최종 표시 순서를 분리해 보존한다. 숫자가 없는 프롤로그·외전의 제목과 실제 목차를 검토 표본에 포함한다.

## 10. 검증 방식과 도입 순서

### 10.1 정확도 평가

기존 묶음 전체를 정답으로 쓰지 않는다. 세 화면의 게시판과 AA·번역·창작·소개 게시판을 나누고, 짧은 제목·분할 회차·중복·번역자 교대·완결·게시판 이동·누락을 포함한 표본을 만든다. 쉽게 처리되는 큰 작품만 평가하면 precision-first 규칙의 실제 누락이 숨는다.

측정값은 구분한다.

- 잘못 연결한 글의 비율과 서로 다른 작품을 합친 그룹 수.
- 같은 작품인데 분리된 그룹 수와 정답 회차 대비 포함률.
- 회차 순서 정확도, 중복·겹침·누락 의심 검출의 정확도.
- 자동 승인/보류/제외 비율과 보류 이유별 건수.
- 재실행 시 ID·순서 변경량, 기존 작품 제거량, 사용자 보정 보존율.
- preview 시간, export 시간, index·shard 크기, 목록 첫 표시 시간.

정답 라벨이 없는 현재 단계에서는 수치 목표를 ‘검증된 정확도’로 제시하지 않는다. 오병합 비용이 크므로 새 규칙은 표본 검토 후 활성화하고, coverage 증가만을 성공 기준으로 삼지 않는다.

### 10.2 최소 회귀 시나리오

| 영역 | 통과 조건 |
|---|---|
| 수집 연결 | 새 3화가 같은 작품에 한 번만 연결; 재실행 동일 결과 |
| 충돌 격리 | 2화 중복이 발견돼도 기존 정상 회차 전체가 사라지지 않음 |
| 회차 파싱 | 1화 (1)/(2), 시즌 재시작, 범위 겹침, 역방향 범위, 막간, 외전 번호를 구별 |
| 동명 작품 | 같은 게시판·다른 창작자·서로 다른 작품을 자동 합치지 않음 |
| 번역 교대 | 작성자 변경만으로 검증된 같은 원작을 분리하지 않음 |

### 10.3 권장 실행 순서

1. F02·F03의 기록 보존과 상태 계산부터 수정하고, F04의 요청 경쟁을 막는다. **1차 적용.**
2. 전체 후보 목록과 legacy 대비 추가·분리·병합·제외 이유를 출력한다. 현재 preview는 `largest`에 `groups[:50]`만 담으므로 작은 오분류·누락을 감사하기 어렵다(`scripts/preview_collections.py:68`).

5. 별칭·게시자·보존 상태 색인과 화면 편의를 추가한다. 성능 변경은 측정 결과에 따라 진행한다.

1차는 Reader와 membership export만 손댔다. 수집 경로·canonical 스키마·새 Python 패키지는 아직 열지 않는다.

남은 검증은 legacy 원래 생성기 확인, 원본 목차에 대한 정답 표본 작성, 현재 운영 release와 최신 DB 대조, 네트워크 지연·장애를 주입하는 브라우저 E2E, 실제 목록/export 성능 측정이다. 따라서 본문에서 코드상 위험·실행 재현·데이터 관찰·기능 제안을 구분했다.

## 12. 추가 조사 — 알고리즘·라이브러리 선택

2026-09-20 후속 요청에 따라 공식 문서·프로젝트·논문을 조회했다. 아래는 ReDSTM에 대한 적용 판단이며, 각 프로젝트의 일반 기능 설명과 구분한다. ‘최신’이라는 이유만으로 우선하지 않고 현재 데이터와 실행 구조에 맞는지를 기준으로 삼았다. 2025년 임베딩·entity matching 연구도 포함하지만, 이를 2026년 전체 분야의 최신·최고 성능으로 주장하지 않는다.

**우선 실험할 조합은 다중 blocking + RapidFuzz 후보 검색 + 명시적 충돌 규칙 + Hypothesis 검증이다.** 한국어 검색은 기존 포함 검색을 기준선으로 두고 FTS5/문자 n-gram을 비교하며, Kiwi와 의미 검색은 별도 실험으로 단계적으로 붙이는 편이 좋다. 아래 도구를 모두 설치하자는 제안은 아니다.

### 12.2 RapidFuzz와 다중 blocking — 가장 먼저 실험할 부분

RapidFuzz는 문자열 유사도와 후보 추출 API를 제공한다. `process.extract`류로 상위 후보를 얻을 수 있고 `score_cutoff`도 있다. 특히 `token_set_ratio`는 한 문자열의 토큰이 다른 문자열에 포함되면 100점이 나올 수 있다. [공식 유사도 설명](https://rapidfuzz.github.io/RapidFuzz/Usage/fuzz.html), [후보 검색 API](https://rapidfuzz.github.io/RapidFuzz/Usage/process.html).

프로젝트 적용안:

- raw title, 회차를 분리한 base, 공백 정규화 key를 각각 보존한다. `리메이크`, `외전`, `2부`를 무조건 지워 유사도를 올리지 않는다.
- 정확 base 일치, 원본 작품 URL 일치, 게시판+희소한 제목 n-gram, 게시자+제목 일부 일치 등 여러 경로에서 후보를 모은다. 한 blocking 규칙만 쓰면 그 규칙 밖의 정답을 영원히 놓칠 수 있다. 여러 규칙의 합집합으로 비교 대상을 만드는 방식은 Splink 문서에도 설명되어 있다. [Blocking rules](https://moj-analytical-services.github.io/splink/topic_guides/blocking/blocking_rules.html).
- 전체 약 28만 글의 모든 쌍을 비교하지 않는다. 먼저 기존 작품·후보 base로 축약하고, 정규화된 제목의 문자 2~3-gram 역색인에서 겹치는 후보만 모은다. 짧은 제목에는 더 엄격한 보조 근거를 요구한다.
- 후보마다 전체 문자열 유사도, 추가·삭제된 단어, 회차 충돌, 원본 URL, 게시자 관계를 따로 표시한다. 95점 같은 임계값 하나로 자동 병합하지 않는다.
- `본편 제목`과 `본편 제목 외전`을 token-set 고득점만으로 합치면 안 된다. 문자열 점수는 동일 작품일 확률도 아니다.
- 자동 승인, 검토 필요, 제외의 세 구간을 두고 임계값은 실제 라벨 표본에서 정한다. 창작과 번역의 게시자 일치 의미가 달라 게시판 역할별 평가가 필요하다.

기대 효과는 기존 9,430개 신규 후보에 대한 근거 확장과 exact-base 밖의 누락 탐색이다. 실제 개선 건수·오병합률은 아직 측정하지 않았다.

### 12.3 회차 파싱 — 순서 정보를 먼저 구조화

파서 라이브러리가 한국어 연재 제목의 의미를 알아서 이해하지는 않는다. 먼저 `제목 / 시즌 / 부 / 회차 / 분할 / 종류 / 상태 태그`를 단계적으로 추출하는 문법을 정의해야 한다.

제안하는 해석 예시는 `작품 2부 13화 (2) [완결]` → base `작품`, 부 `2`, 회차 `13`, 분할 `2`, 완료 표식이다. `[완결]`이 작품 전체인지 현재 부인지 원문에서 확인되지 않으면 범위는 미상으로 둔다. `상·중·하`, `전·후`, `외전 1`, `막간`, `1~3화`는 각각 구조가 다르다.

처음에는 기존 `re`와 dataclass로 충분하다. 정규식의 실행 순서에 따라 해석이 자주 달라지고 괄호·중첩·범위 문법이 커질 때 **Lark**의 명시적 grammar와 parse tree를 비교한다. Lark는 Earley·LALR 등의 파서를 제공하지만, 후보 해석이 여러 개라는 사실을 숨기지 않고 보류할 정책은 애플리케이션에서 정해야 한다. [Lark 공식 저장소](https://github.com/lark-parser/lark).

원본 목차나 ‘이전/다음 편’ 링크가 있으면 그것이 정규식보다 강한 순서 근거가 될 수 있다. 게시물 사이에 `A가 B보다 앞` 간선을 만들고 **위상 정렬**로 충돌 없는 부분 순서를 얻는다. Python 표준 `graphlib.TopologicalSorter`는 순환을 감지한다. 관계없는 노드의 순서는 안정적인 보조 키를 따로 정하고, 일반 게시판 다음 글 링크를 작품 다음 편으로 오인하지 않아야 한다. [Python graphlib](https://docs.python.org/3/library/graphlib.html).

### 12.4 Kiwi — 한국어 검색에 유용하지만 제목을 고쳐 쓰는 도구는 아님

Kiwi의 Python API인 `kiwipiepy`는 형태소 분석, 사용자 사전, 띄어쓰기·오타 관련 기능을 제공한다. 원문 토큰과 위치도 얻을 수 있다. [공식 저장소·API 안내](https://github.com/bab2min/kiwipiepy).

여기서는 `호그와트에서`를 찾을 때 `호그와트`가 검색되고, 조사 차이 때문에 후보가 빠지지 않도록 **검색용 토큰을 추가하는 용도**가 적합하다. 작품명·캐릭터명·게시자명은 사용자 사전에 넣을 수 있다. 다만 판타지 고유명사·일본어 음역·의도적인 비문·AA 기호가 일반 한국어와 달라 오교정 가능성이 있다.

따라서 원래 제목·정규화 제목·형태소 토큰·문자 n-gram을 별도로 두고, 형태소 분석 결과가 raw 제목의 exact match를 대체하지 않게 한다. 모든 본문을 상시 분석하기보다 제목·별칭·소개문부터 오프라인 색인해 모델 크기와 처리 비용을 측정한다. 한국어가 아닌 제목은 다른 경로로 처리한다.

### 12.5 FTS5와 MiniSearch — 서버 후보 검색과 브라우저 UX를 구분

SQLite FTS5의 `unicode61`은 Unicode 기반 토큰화이며 한국어 형태소 분석기가 아니다. `trigram`은 부분 문자열 검색에 도움이 되지만 `MATCH`의 3글자 미만 검색어는 매치하지 않는다. 짧은 `LIKE`는 fallback scan이 될 수 있다. [SQLite FTS5 공식 문서](https://www.sqlite.org/fts5.html).

이번 추가 조사에서 설치 없이 프로젝트 Python으로 확인했다.

- SQLite 버전: **3.50.4**, 메모리 DB에서 FTS5 trigram 생성 성공.
- 제목 `호그와트에서 마왕이 되었다`에 `MATCH '호그와트'`: unicode61 0건, trigram 1건.
- 같은 제목에 `MATCH '마왕'`: 둘 다 0건. trigram 테이블의 `LIKE '%마왕%'`는 1건.

즉 FTS를 넣는 것만으로 현재 `includes` 검색보다 항상 검색률이 높아지지 않는다. 1~2글자·초성·고유명사·일본어·영문 혼합을 별도 평가해야 한다. 초성 검색은 가벼운 보조 key로 추가할 수 있지만 정답 작품 병합에는 사용하지 않는다.

저장소에 `scripts/profile_text_fts.py`가 이미 unicode61/trigram 비교를 구현한다. 단, 이 스크립트는 legacy의 `content_html` 등 컬럼을 기대하므로 현재 canonical DB를 인자만 바꿔 바로 넣을 수 있는 도구로 안내하지 않는다. 측정 방법을 재사용하되 canonical projection에 맞추는 작업이 필요하다.

Reader는 정적 index와 Worker 구조다. canonical DB에 FTS를 추가해도 브라우저 검색이 자동으로 그것을 쓰지는 않는다. 오프라인 후보 분석은 SQLite, 사용자 검색은 기존 `search-core.js` 또는 정적으로 내보낸 색인을 쓰는 식으로 경계를 나눈다.

**MiniSearch**는 브라우저·Node에서 실행되며 prefix/fuzzy 검색, 필드 가중치, 자동 제안을 제공한다. 기본 토큰화는 공백·구두점 분리이므로 한국어용 토큰 전략은 별도로 필요하다. [MiniSearch 공식 문서](https://lucaong.github.io/minisearch/).

작품 18,369개의 제목·별칭·게시자부터 기존 Worker 안에서 비교하는 것이 적당하다. 본문 전체를 모바일 메모리에 넣거나 한국어 원문 토큰과 모든 n-gram을 무제한으로 중복 적재하지 않는다. 네트워크 크기·index build 시간·메모리·p95 검색 지연·검색 성공률을 함께 비교한다. 기존 날짜순 둘러보기와 relevance 검색순도 구분해야 한다.

### 12.6 Splink와 dedupe — 정규식 다음 단계의 entity resolution

**Splink**는 Fellegi–Sunter 기반 확률적 연결을 지원한다. 공식 문서도 서로 강하게 종속되지 않는 여러 필드가 있을 때 적합하며, 단일 이름 문자열만 있는 문제를 주요 용도로 보지 않는다고 설명한다. [확률적 연결 설명](https://moj-analytical-services.github.io/splink/topic_guides/theory/probabilistic_vs_deterministic.html), [적합한 데이터 조건](https://moj-analytical-services.github.io/splink/).

현재 제목에서 파생한 base·토큰·접두어를 ‘독립적인 세 근거’처럼 취급하면 같은 정보를 중복 계산하게 된다. 원작 URL·게시자 역할·출처 목차·회차 구조 등 별도 근거가 쌓였을 때 제목 일치보다 더 설명 가능한 판정이 가능하다. 또 게시물마다 회차가 다르다는 것은 정상이다. 중복 레코드 제거용 예제를 그대로 가져와 서로 다른 회차를 중복으로 삭제해서는 안 된다. 목표 entity는 ‘작품’이고 원글은 그 구성원이라는 모델을 명시해야 한다.

**dedupe**는 사람이 제공한 match/distinct 라벨을 학습하고, `uncertain_pairs()`로 검토할 쌍을 제시하는 API가 있다. [공식 프로젝트](https://github.com/dedupeio/dedupe), [학습·라벨링 API](https://docs.dedupe.io/en/latest/API-documentation.html).

우선 active learning의 아이디어만 적용해도 효과가 있다. 무작위로 1,000개를 훑는 대신 규칙 간 불일치, 높은 유사도+회차 충돌, 작은 차이로 분리된 대형 작품, 신규 parser가 바꾼 판정부터 검토한다. 여기에 무작위 표본도 섞어 자동 승인 쪽의 숨은 오류를 감시한다. 초기에는 CSV/JSON 검토 목록으로 충분하고, 반복 라벨링 규모가 커지면 dedupe와 Splink 중 목표에 맞는 하나를 비교한다.

### 12.7 본문 중복 탐지 — 해시와 MinHash를 작품 판정과 분리

정확히 같은 본문은 기존 해시 체계를 활용한다. 전체 보존 payload 해시는 metadata나 댓글 변화까지 반영할 수 있으므로, 재게시 비교에는 무엇을 해시했는지 확인하고 필요한 경우 본문 전용 fingerprint를 둔다. 동일 본문이어도 원본 ID가 다른 글은 삭제하지 않고 관계만 표시한다.

일부 문장 수정·머리말 추가가 있는 근접 중복이 문제라면 **datasketch MinHash LSH**로 본문 shingle 집합이 유사한 후보를 찾을 수 있다. LSH는 근사 후보 검색이라 false positive/negative가 있을 수 있으며 반환된 후보를 실제 유사도로 재검증해야 한다. [datasketch 공식 문서](https://ekzhu.com/datasketch/lsh.html).

이는 ‘같은 13화를 다시 올렸는가’ 탐지에는 유용하지만 ‘13화와 14화가 같은 작품인가’의 직접 기준은 아니다. 긴 연재는 회차마다 본문이 달라 정상적인 낮은 유사도가 나오고, AA는 반복되는 도형·서명·템플릿 때문에 다른 글도 높게 나올 수 있다. 본문 정규화는 비교용 복사본에만 하고 원본 AA 공백·기호를 수정하지 않는다.

## 13. 의미 검색·최신 모델을 쓰는 경우

### 13.1 검색과 동일 작품 판정은 목표가 다름

‘호그와트에서 가게 운영하는 이야기’처럼 정확한 제목을 기억하지 못한 검색에는 임베딩이 유용할 가능성이 있다. 반면 ‘호그와트 배경의 서로 다른 두 팬픽’도 의미적으로 가까우므로 코사인 유사도가 높다는 이유로 하나의 작품으로 합치면 안 된다.

비교 후보는 **Qwen3-Embedding-0.6B**와 **BGE-M3**다. Qwen3 계열은 다국어 embedding과 reranker 모델을 제공하며, BGE-M3는 dense·sparse·multi-vector 기능을 제공한다. 이름은 현재 확인한 실험 후보이며 ReDSTM 최적 모델로 확정한 것은 아니다. [Qwen 공식 발표](https://qwenlm.github.io/blog/qwen3-embedding/), [Qwen 공식 저장소](https://github.com/QwenLM/Qwen3-Embedding), [BGE-M3 제작자 모델 카드](https://huggingface.co/BAAI/bge-m3).

추천 실험은 제목+확인된 별칭+소개문을 작품별로 한 번 임베딩하고, 원래 문자열 검색을 계속 우선 보존하는 방식이다. 매 회차 본문 전체를 처음부터 임베딩할 필요는 없다. Qwen3의 0.6B 모델도 FP16 가중치만 단순 계산으로 약 1.2GB이므로 기존 문서의 700MiB runner 예산 안에 같은 프로세스로 얹는 설계는 맞지 않는다. 이 수치는 실행 측정이 아니라 파라미터 수×2바이트 계산이며 실제 메모리는 더 든다. 별도 PC 배치·격리된 실험 환경에서 비용을 먼저 측정한다.

작품 요약 약 1.8만 개에 대한 실험은 정확한 벡터 비교를 기준선으로 삼을 수 있다. 예를 들어 18,369×768차원×float32는 벡터 배열만 약 54MiB다. 이는 선택한 768차원 표현의 산술 예시이며 모델 기본 차원이나 전체 서비스 메모리 측정이 아니다. 성능 요구가 확인되기 전 전용 벡터 DB나 HNSW 서버부터 추가할 이유는 적다. 브라우저에 이 배열을 전송하는 것이 적합한지는 별도 문제다.

### 13.2 Hybrid retrieval + RRF + reranker

문자열/BM25 계열과 embedding 결과를 함께 쓰면 점수 척도가 다르다. **Reciprocal Rank Fusion(RRF)**은 각 목록의 순위를 이용해 결합한다. 이 기법을 쓰기 위해 Elasticsearch를 설치할 필요는 없다. [RRF 설명과 계산](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion).

제안 흐름은 `정확 제목·별칭 → 문자열 후보 + 의미 후보 → RRF → 필요 시 상위 소수 rerank`다. exact match와 사용자 선택 필터는 별도로 보장한다. RRF 값 역시 ‘같은 작품일 확률’이 아니다.

reranker는 query와 각 후보를 함께 읽어 재정렬하므로, 전체 작품을 매번 재평가하기보다 검색이 좁힌 후보에 적용한다. Sentence Transformers는 이런 retrieve-and-rerank 구조를 설명한다. [공식 예제](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html).

단계마다 실제 검색어로 nDCG@10·MRR·Recall@K와 응답 시간을 비교해야 한다. 한국어 팬픽 제목·AA·희귀 고유명사에서는 일반 벤치마크 순위가 그대로 재현되지 않을 수 있다. 의미 후보가 추가 정답을 거의 찾지 못하거나 reranker가 exact 제목을 밀어내면 해당 단계는 제외한다.

### 13.3 LLM은 예외 해석·검토 보조부터

2025년 COLING의 *Match, Compare, or Select?*는 LLM에 entity matching을 시키는 문제 형식을 비교하고, 2025년 11월의 *Structured Multi-Step Reasoning for Entity Matching*은 단일 단계 대신 구조화된 추론을 탐구한다. 이 연구들은 최근 방향을 참고할 자료이지 한국어 작품 목차에서 정확도를 보장하는 근거가 아니다. [COLING 논문](https://aclanthology.org/2025.coling-main.8/), [2025-11 preprint](https://arxiv.org/abs/2511.22832).

여기서 적용할 수 있는 아이디어는 애매한 제목을 한 번에 ‘같은 작품/다른 작품’으로 찍게 하기보다, 먼저 회차 구조와 근거를 추출하고 후보와 비교하게 하는 것이다. 출력은 `후보 ID 또는 미확정`, `원문 근거 위치`, `충돌 사유`, `추출한 회차 필드`처럼 검증 가능한 형식으로 제한한다. 없는 원작 제목·누락 회차를 생성한 결과는 수용하지 않는다.

raw 제목과 목차 링크만으로 해결되지 않는 보류 사례에 한정하고, 자동으로 DB를 병합하는 권한은 주지 않는다. 실행 모델·prompt·입력 hash를 함께 남겨 같은 결과를 감사할 수 있게 한다. 이번 조사에서 LLM 호출·본문 외부 전송은 하지 않았다.

## 14. 안정성·검토 품질·개인화에 쓸 기법

### 14.1 Hypothesis와 metamorphic testing

Hypothesis는 입력을 생성하는 property-based testing을 제공하고, stateful testing은 행동의 순서까지 생성할 수 있다. [기본 문서](https://hypothesis.readthedocs.io/en/latest/), [상태 기반 테스트](https://hypothesis.readthedocs.io/en/latest/stateful.html).

이 프로젝트에서 값이 큰 속성은 다음과 같다.

- 입력 순서를 섞어도 작품 소속·ID·순서가 같음.
- 전각 숫자·공백·알려진 표기만 바꿔도 같은 회차로 해석됨. 모든 문장부호 삭제를 동등한 변환으로 가정하지 않음.
- 무관한 글 추가가 기존 작품을 삭제하거나 재번호 매기지 않음.
- 같은 변경을 두 번 적용해도 결과가 같음.
- 재연재·원본/번역·본편/외전의 강한 분리 제약을 유사도가 덮지 않음.
- 글 추가 → 읽음 → unavailable → 재보존 → 재색인 뒤에도 stable ID와 기록이 유지됨.

순열·변형 후 지켜져야 할 관계를 확인하는 **metamorphic testing**은 모든 실데이터의 정답이 없어도 가능하다. 다만 업무상 불변 조건을 잘못 정의하면 버그가 아니라 정상 동작을 금지하게 되므로, 이번에 재현한 작은 실패 예제를 먼저 고정하고 범위를 넓힌다. pytest 환경은 이미 있어 새 테스트 프레임워크를 갈아탈 필요가 없다.

### 14.2 학습·평가 데이터 누출 방지와 확률 보정

작품의 1화는 학습, 2화는 평가에 무작위 배치하면 제목이 거의 같아 지나치게 좋은 성능이 나온다. 작품 단위로 분리하고, 가능하면 시기·게시판·게시자 변경 사례도 따로 평가한다. 랜덤한 무관 쌍만 음성으로 넣지 말고 동명 작품·리메이크·외전·다른 번역판 등 어려운 음성을 포함한다.

학습 모델의 점수를 확률로 표시하려면 calibration도 평가한다. scikit-learn은 확률 calibration 도구를 제공하지만 별도 calibration 데이터가 필요하며 표본이 작으면 복잡한 보정이 과적합할 수 있다. [공식 calibration 설명](https://scikit-learn.org/1.8/modules/calibration.html).

초기 규칙에는 억지 확률 대신 ‘원본 URL 일치’, ‘회차 중복’, ‘검토 필요’라는 근거를 표시하는 편이 낫다. 예를 들어 독립·대표 표본이라는 가정 아래 300개 자동 승인에서 오류가 0이어도, 단측 95% 이항 상한 `1 - 0.05^(1/300)`은 약 1%다. 300건 무오류만으로 99.9% 정확도를 주장할 수 없다. 실제 작품 회차는 상관되어 있으므로 작품 단위 평가가 특히 중요하다.

### 14.3 증분 갱신과 shadow evaluation

현재 해시·export state를 재사용하되, 작품 분석 입력만의 fingerprint를 구분한다. 제목·관련 URL·게시자 역할·규칙 버전·수동 override가 같으면 기존 파싱·판정을 재사용할 수 있다. 본문 비교가 판정에 참여했다면 해당 본문 버전도 fingerprint에 넣어야 한다.

제목 수정으로 base가 바뀌면 **새 block뿐 아니라 옛 block도** 다시 평가한다. 삭제·원복·override 변경·작품 병합/분리도 영향을 받은 소속과 shard를 무효화해야 한다. 수집 시각 하나만 cursor로 쓰면 같은 시각·역순 적재를 놓칠 수 있으므로 기존의 단조 증가 변경 식별자 등 확실한 기준을 재사용한다.

새 알고리즘은 실제 테이블을 교체하기 전에 같은 입력으로 병렬 산출물만 만드는 **shadow evaluation**을 거친다. 이전 버전과 소속 추가·제거·순서·종류·ID 변화를 비교하고 검토가 끝난 결과만 적용한다. 이것은 별도 분산 시스템 도입이 아니라 버전 있는 후보 결과와 diff를 남기는 실행 방식이다.

### 14.4 IndexedDB와 Dexie

500건 절단 문제의 첫 해법은 영구 진행 기록을 자르지 않는 것이다. 기록이 늘어나 localStorage 전체 JSON 재작성 비용·용량 문제가 실제로 나타나면, 글별 부분 갱신이 가능한 IndexedDB를 비교한다. **Dexie**는 IndexedDB를 다루는 API와 transaction 기능을 제공한다. [Dexie 공식 문서](https://dexie.org/docs/index).

DB 교체만으로 기존 데이터 보존이 보장되지는 않는다. migrate·재실행·실패 복구·내보내기/가져오기·다중 탭을 확인해야 한다. 특히 Dexie의 `bulkPut`을 transaction 밖에서 실행하면 일부 실패에도 성공한 일부 기록이 남을 수 있으므로 원자적 import에는 transaction을 써야 한다. [bulkPut 공식 주의사항](https://dexie.org/docs/Table/Table.bulkPut%28%29).

### 14.5 개인 장서에 맞는 추천·발견 기능

한 사람의 보존 장서에서는 협업 필터링 학습보다 ‘읽던 작품에 새로 붙은 편’, ‘완독 작품의 외전’, ‘같은 작성자’, ‘미보존 회차가 복구됨’이 먼저 유용할 수 있다. stable ID·관련 작품·사용자의 마지막 확인 시점·membership 변경 이력만으로 구현할 수 있다.

의미 임베딩을 도입했다면 ‘비슷한 작품’ 추천에도 재사용할 수 있지만, 같은 작품의 판본·중복 글이 추천 목록을 채우지 않도록 구분한다. 회차 수·조회수·최신성만으로 순위를 만들면 장편·오래 수집된 게시판에 편향될 수 있어, 사용자에게 추천 이유를 보여주고 끌 수 있게 한다. 이는 알고리즘 성능이 검증된 결과가 아니라 본 프로젝트에 대한 제품 제안이다.

## 15. 실제 도입 판단과 추가 조사 범위

### 15.1 제안하는 세 단계

| 단계 | 사용할 것 | 확인할 결과 |
|---|---|---|
| 1: 생성 정확도·안정성 | 기존 re/SQLite + 다중 blocking + RapidFuzz 후보 + Hypothesis | 새로 찾은 정답, 오병합, 충돌 격리, 결정성·멱등성 |
| 2: 검색·검토 편의 | 별칭·원본 링크 색인 + FTS5 비교 + 필요 시 MiniSearch/Kiwi | 실제 검색 성공률, 1~2글자·고유명사 품질, 검토 시간 |
| 3: 의미·학습 고도화 | active learning, Splink 또는 dedupe, embedding/RRF/reranker, LLM 예외 처리 중 필요한 것 | 기준선 대비 추가 이득, 메모리·지연·비용, 재현·감사 가능성 |

새 라이브러리를 하나만 실험한다면 **RapidFuzz**, 개발 검증까지 포함하면 **Hypothesis**를 다음 후보로 권한다. 검색 UX가 주목적이면 **MiniSearch**, 한국어 질의 실패가 주목적이면 **Kiwi**를 별도 비교한다. 고유 제목·회차 구조가 해결되지 않은 상태에서 embedding으로 그룹을 통째로 다시 만드는 방식은 권하지 않는다.

### 15.2 호환성과 실제 확인 수준

- 프로젝트는 Python `>=3.14,<3.15`, Node `>=22`를 선언한다. 조사 시 프로젝트 환경에 `rapidfuzz`, `hypothesis`, `kiwipiepy`, `lark`, `splink`, `dedupe`, `sentence_transformers`, `datasketch`는 설치되어 있지 않았다.
- 이 목록의 추천은 설치·통합 완료를 의미하지 않는다. 특히 native 확장·모델 runtime은 Python 3.14, Windows 개발 환경, 실제 runner의 OS/CPU에 맞는 wheel과 실행 메모리를 별도 확인해야 한다. 단순 `Requires-Python` 범위만으로 호환성을 확정하지 않는다.
- 새 패키지·모델 다운로드·설치·프로젝트 코드 변경은 하지 않았다. 공식 기능을 조사하고 현재 SQLite의 메모리 DB에서만 검색 동작을 실행했다.
- 이번 추가분은 기존 테스트 40개를 새 라이브러리의 검증으로 주장하지 않는다. 해당 테스트 결과는 §11의 기존 코드 검증이며, 추가 도구의 속도·정확도 비교는 아직 실행 전이다.
- 본문 링크는 조회한 공식 문서·제작자 저장소·모델 카드·원 논문이다. 링크의 최신 문서는 바뀔 수 있으므로 실제 도입 시 버전·모델 revision·설정·평가 표본을 고정해 결과와 함께 남긴다.

### 16.2 B01 — P1: 4원소 membership은 구형 Reader에 비호환

**근거:** 현재 `edge/public/app.js:1843`의 `loadCollectionMembership`은 3/4원소 모두 수용하지만, HEAD의 이전 구현은 `member.length !== 3`이면 예외를 던진다. export는 tuple을 4개로 바꾸면서 membership `schema_version: 1`과 `membership-v2` prefix를 유지한다(`scripts/export_static.py:1539`).

신 Reader가 구 데이터를 읽는 것은 가능하지만 **구 Reader가 신 데이터를 읽는 방향은 불가능**하다. 이미 열려 있는 옛 탭이 이후 처음 membership을 요청하거나, 신 데이터 게시 후 Reader만 롤백하면 작품 소속·이전/다음 탐색 등이 깨질 수 있다. 실제 운영 발생은 확인하지 않았으며, 위 코드는 호환성 실패 조건을 명확히 보여준다.

이것은 F08 전체 release 공유 설계를 뒤로 미루는 것과 별개다. 데이터 형식을 바꾸는 이번 변경에서 해결해야 하는 배포 계약이다.

권장 선택:

- 가장 작은 호환 설계는 기존 3원소 `members`를 유지하고, 객체의 선택적 가용 정보 필드(예: 미보존 stable ID 목록)를 추가하는 방식이다. 구 Reader가 모르는 필드를 무시할 수 있도록 기존 validation 경계를 확인한다.
- 4원소를 유지한다면 신 형식 식별·클라이언트 capability·호환 manifest 또는 구 탭 갱신 동작과 롤백 절차를 명시한다. 단순히 schema 번호만 올리면 구 Reader가 갑자기 읽을 수 있게 되는 것은 아니다.
- `새 Reader 먼저 배포`만으로 이미 열린 구 탭까지 교체되는 것은 아니다. 구/신 Reader × 구/신 데이터 조합을 테스트하고 실제 지원 범위를 기록한다.

**배포 전 조건:** 지원한다고 정한 혼합 버전 경로와 rollback 조합이 통과해야 한다. 현 상태를 ‘localStorage 계약은 그대로이므로 호환성도 그대로’라고 설명하면 안 된다. 변경된 것은 archive wire format이다.

### 16.3 B02 — P1: ‘다음 export부터 반영’은 무조건 성립하지 않음 [실행 재현]

**근거:** `_snapshot_fingerprint`는 데이터 projection/topology를 해시하지만 이번 membership 출력 형식 변경을 반영하는 버전은 포함하지 않는다(`scripts/export_static.py:716`). `_incremental_export_static`은 fingerprint가 같으면 aggregate 생성 전에 `incremental_noop`로 반환한다(`:2108` 부근).

기존 테스트의 작은 canonical fixture로, membership을 3원소로 직렬화한 정상 baseline을 만든 뒤 직렬화 함수를 현재 구현으로 복원했다. DB를 바꾸지 않고 `export_static(..., incremental_only=True)`를 실행한 결과:

```text
mode: incremental_noop
membership tuple lengths: [3, 3]
```

따라서 정확한 안내는 **‘새 형식으로 aggregate가 실제 재생성되고 그 release가 publish된 뒤 반영’**이다. 코드만 배포하거나 같은 R2 객체를 다시 publish하는 것으로는 바뀌지 않는다.

개선안:

- export 형식/알고리즘 revision을 state 비교에 반영하거나, 기존 post object를 재사용하면서 collection aggregate만 명시적으로 갱신하는 경로를 둔다.
- 운영 예산이 있으므로 무조건 대규모 full export를 실행하라는 뜻은 아니다. 실제 재생성 범위·자원·시간을 정하고 실행 결과의 membership payload와 release 참조를 확인한다.
- 재생성 후 다시 export했을 때에는 noop가 되어야 한다. 변경 감지 때문에 매번 전체를 다시 만드는 회귀도 막는다.

### 16.4 B03 — P1: export 검증이 가용 비트의 의미를 검사하지 않음 [실행 재현]

**근거:** `validate_release`는 4번째 값이 0/1인지만 확인한 뒤 `membership_rows`에는 `(collection_id, position)`만 보관한다(`scripts/export_static.py:1098`, `:1112`). detail로 만든 expected 값도 ID·position뿐이다(`:1151`).

작은 fixture의 exporter 직렬화에만 오류를 주입하여 가용 값을 반대로 만들고, 나머지 객체·해시·manifest는 실제 exporter로 정상 생성했다. resulting membership은 다음과 같았다.

```text
[1, 1, 1, 0]   # 실제 본문이 있는 글을 unavailable로 잘못 표기
[99, 1, 2, 1]  # 실제 본문이 없는 글을 available로 잘못 표기
```

이 상태에서 **현재 `validate_release`가 통과**했다. 파일을 임의로 깨뜨려 checksum을 우회한 실험이 아니라, 잘못된 의미를 가진 정상 형식의 export를 validator가 잡는지 확인한 것이다. F03의 원인인 분자·분모 불일치를 게시 전 검증이 아직 차단하지 못한다.

또한 Python의 `member[3] not in {0, 1}`만으로는 bool·0.0·1.0을 엄격히 거절하지 못한다. JS는 `!== 0/1`을 사용해 boolean을 거절하므로 validator/Reader 경계도 일치시키는 것이 좋다.

개선과 검증:

- 새 형식에서는 각 비트를 detail의 `object_key is not None`과 비교하고, summary의 unavailable_count 및 소속 수와도 일관성을 확인한다.
- 구 3원소는 ‘가용 정보 없음’으로 별도 처리한다. 구 형식에도 없는 정보를 검증했다고 간주하지 않는다.
- 정상 가용/미보존, 비트 반전, 잘못된 타입, unknown collection/position에 대한 작은 exporter 회귀 테스트를 추가한다.
- 실제 publish 경로가 사용하는 validator도 확인한다. `validate_incremental_release`는 현재 finalized state·참조·개수 중심의 별도 경로이므로, full validator만 강화하고 게시 경로에서는 실행되지 않는 검증이 되지 않게 한다(`:1188`).

### 16.5 B04 — P1: Reader에서 벗어날 때 요청 세대가 무효화되지 않음

**근거:** `readerViewId`를 증가시키는 곳은 `openCollectionDetail`(`app.js:1627`)과 `loadPost`(`:1930`)뿐이다. `showDestination`(`:953`)과 목록으로 돌아가는 흐름은 진행 중 요청을 무효화하지 않는다.

남은 시나리오:

1. 작품 A 또는 본문을 연다. 응답이 늦다.
2. 사용자가 홈·둘러보기로 이동하거나 Back으로 Reader에서 나간다.
3. 다른 Reader 요청이 없으므로 viewId는 그대로다.
4. 이전 응답이 최신으로 인정되어 상세·본문과 URL을 다시 반영한다.

실제 `openCollectionDetail` 함수를 Node VM에서 실행하고, 응답 대기 중 `showDestination`의 목적지 변경에 해당하는 상태를 적용했다. 늦은 응답이 `setScope`의 화면 반영 경계까지 진행함을 확인했다. 이는 함수 수준 재현이며 실제 브라우저 Back까지 실행한 검증은 아니다.

개선: Reader 선택을 시작할 때뿐 아니라 **Reader 선택을 취소하는 내비게이션에서도** 같은 세대를 무효화하고 요청을 취소한다. Reader 위에 잠깐 여는 설정처럼 기존 내용을 유지하는 행동과 실제 이탈은 구분한다.

추가 E2E는 A→B 응답 역전, 본문↔목차 역전뿐 아니라 A 대기→홈, A 대기→Back, 오래된 실패 응답, busy 해제까지 포함해야 한다. 현재 viewer.spec.js에는 이 지연 응답 시나리오가 명시적으로 없다.

### 16.6 B05 — P2: F07의 미확인 상태가 행에는 반영되지 않고 전역 Set이 경합

**행 표시 문제:** `renderCollectionCatalog`는 실패 게시판을 읽기 필터에서 제외하지만, ‘전체’ 목록의 `collectionItemElement`는 해당 작품의 progress가 없으면 여전히 0으로 계산한다(`app.js:1528`). 이미 읽던 작품도 ‘시작하기’로 표시되고 상단에만 ‘일부 읽기 상태 미확인’이 붙는다. 필터 제외와 별개로 행도 ‘읽기 상태 미확인 · 목차 보기’처럼 상태를 보존해야 한다.

**공유 상태 문제:** `collectionReadingProgress`는 호출마다 전역 `collectionProgressFailedBoards`를 새 Set으로 교체한 후 비동기 catch에서 다시 전역 Set에 기록한다(`:1594`, `:1620`). 홈·목록·보관함이 같은 함수를 호출하므로 이전 호출의 늦은 실패가 새 호출 결과에 섞일 수 있다.

실제 함수를 두 번 호출하는 Node VM 재현에서 새 호출이 성공한 뒤 이전 호출을 실패시키자, 새 전역 Set에 이전 실패 게시판이 추가되었다. 각 요청의 결과는 `{progress, failedBoards}`처럼 로컬로 묶어 반환하고, 해당 UI의 최신 요청일 때 함께 반영하는 편이 명확하다.

**추가 한계:** catch 덕분에 최종 실패는 격리하지만 `Promise.all` 대기는 그대로라 응답이 끝나지 않는 membership은 전체 목록 표시를 지연시킨다. 현재 선택과 관련된 게시판만 계산하거나 목록을 먼저 보여주고 상태를 나중에 보완하는 방식은 후속 개선이다. 관련 상태 재시도도 제공하면 좋다.

### 16.7 추가 확인 — 즉시 대규모 재설계는 필요 없음

- **F02 기록 보존:** 절단 제거는 맞다. E2E는 500건 이후에도 가장 오래된 identity의 progress=1과 scroll=321, 총 502건을 확인한다. 896편·내보내기/가져오기 왕복은 아직 별도 시나리오가 없다.
- **저장 비용:** history를 제한 없이 보존하면 localStorage 전체 직렬화·저장 비용이 증가한다. 1천·1만 건에서 쓰기 시간과 용량을 측정하고 필요할 때 바꾼다. 이것만으로 지금 IndexedDB를 도입할 이유는 없다.
- **본문→목차 마지막 위치:** `openCollectionDetail`과 Reader를 떠나는 `showDestination`은 `currentSummary`를 비우기 전에 `persistReadingPosition`을 호출한다. 250ms debounce 중 이탈해도 마지막 측정값을 남긴다.
- **F05 행동 테스트:** 앞쪽 미독 E2E는 버튼 문구와 클릭 후 해당 미독 목차 행 focus를 검사한다. 목록에서 generic ‘이어 읽기’를 유지하는 것은 허용 가능한 요약이며 F06과 충돌하지 않는다.
- **실패가 있는 홈·보관함:** 목록 행은 `읽기 상태 미확인`이다. 홈은 확인된 읽는 중만 보여 주고, 전부 실패면 `읽기 상태를 확인하지 못했습니다.`, 일부 실패면 `일부 읽기 상태 미확인`을 붙인다. 보관함 읽는 중은 건수 뒤에 같은 주석을 붙인다.
- **수량 표현:** 18,369는 ‘편’이 아니라 작품/묶음 수이고, 기존 소속 글은 168,102건이다. 새 preview의 누락을 설명할 때 두 단위를 구분한다.

E2E 180건은 다양한 화면 폭을 검증한 좋은 증거지만, 서로 다른 180개 기능 시나리오를 의미하지 않는다. 현재 공통 v2 fixture는 4원소 membership만 사용하므로 구 3원소/신 4원소 호환 조합, release 갱신 no-op, 의미가 잘못된 비트, 지연 내비게이션을 별도 추가해야 한다. 테스트 수보다 이 계약을 직접 실패시킬 수 있는 검사가 중요하다.

### 16.9 다음 에이전트에게 전달할 작업 순서

1. **membership 호환 형식과 갱신 조건부터 확정:** B01·B02. **적용.** 3원소 `members` + 선택 필드 `unavailable`. 데이터 무변경 시 `incremental_collections`로 collection aggregate만 재생성.
2. **새 가용 정보 검증을 완성:** B03. **적용.** `validate_release`와 `validate_incremental_release`가 detail `object_key`와 `unavailable`을 대조한다.
3. **Reader 이탈도 취소 처리:** B04. **적용.** 홈/둘러보기 이동 시 `readerViewId` 무효화. 설정 overlay는 유지.
4. **미확인 진행 상태를 요청별로 격리:** B05. **적용.** `{progress, failedBoards}` 반환. 행은 `읽기 상태 미확인`.
5. 운영 R2는 Oracle control runner의 `publish-if-changed`가 `incremental_collections`를 게시한다. 수집이 돌고 있으면 설치/게시 잠금을 기다린다. 워크스테이션에서 production R2를 직접 쓰지 않는다.
6. 다음 기능 단계는 **작품 dry-run 전체 후보와 기존 소속 diff·정답 표본 작성**이다. parser/RapidFuzz/임베딩/LLM은 그 이후다.

## 16. 1차 구현 (인프라 맞춤)

권장 순서 §10.3의 1번과, 같은 세션에서 안전한 F05~F07을 적용했다. 새 패키지·D1·crawler write path·canonical UNIQUE 변경은 하지 않았다.

| 항목 | 적용 | 비고 |
|---|---|---|
| F02 | 영구 history/scroll을 500건으로 자르지 않음. 홈 최근 목록 표시 제한은 유지 | IndexedDB는 용량 문제 실측 후 |
| F03 | v1은 `object_key` 없는 편 제외. v2는 3원소 `members` + 선택 필드 `unavailable` | 구 Reader는 모르는 필드를 무시. `COLLECTION_EXPORT_REVISION`이 바뀌면 collection aggregate만 재생성 |
| F04 | 작품 상세와 본문이 공유 `readerViewId`. 늦은 응답은 화면을 덮지 않음 | |
| F05 | 본문 0편은 `본문 없음`. 마지막 편 도달+앞쪽 미독은 목차의 `앞쪽 미독 N편 보기` | 자동 이어 읽기는 앞쪽 미독으로 되돌리지 않음 |
| F06 | 목록/홈 요약 행은 추정 회차 숫자 없이 `이어 읽기` | 상세는 실제 목차로 계산 |
| F07 | membership 실패는 해당 게시판만 미확인. 전체 목록은 유지. 읽기 상태 필터에서는 미확인 게시판 제외 | |
| F01, F08, 파서, RapidFuzz | 보류 | 수집 연결은 dry-run·표본 검토 후. 검색 Worker와 작품 index의 release 공유는 다음 |

membership 계약은 `members: [external_post_id, collection_id, position]`에 선택 필드 `unavailable: [external_post_id, ...]`를 둔다. 구 Reader는 `unavailable`을 무시한다. 새 Reader는 그 ID를 보존 불가로 본다. 4원소 tuple은 쓰지 않는다.
