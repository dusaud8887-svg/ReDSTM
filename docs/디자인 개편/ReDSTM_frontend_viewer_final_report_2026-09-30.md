## 1.2 가장 효과가 클 것으로 보는 변화

**첫째, 소스가 아니라 작품과 읽기 상태를 중심에 둔다.**  
‘타입문넷/텍스트/아카라이브’는 데이터 출처로 남기되, 사용자가 매번 저장 방식부터 이해해야 하는 구조를 줄인다. 같은 화면에서 작품을 찾고 읽을 수 있게 하면서 원본 ID·보존본·실패 경계는 유지한다.

**둘째, 서재에는 개성을, 본문에는 안정성을 준다.**  
표지와 색, 작품별 작은 시각 요소, 발췌 카드 등으로 소장감과 식별성을 높인다. 실제 읽는 중에는 작품 테마가 본문 서체·배경을 강제로 바꾸지 못하게 한다.

**셋째, 한국어로 다시 찾는 경험을 제품의 강점으로 만든다.**  
초성 제목 검색, 공백 차이를 허용하는 검색, 기억나는 대사의 정확한 부분 문자열 검색, 작품별 별칭, 앞뒤 문맥과 원문 이동을 결합한다.

**넷째, 장편을 관리하는 ‘회차 도구’를 강화한다.**  
현재 위치, 다음 미열람 구간, 보존 누락, 문장 기록, 검색 위치를 명확히 분리한다. 길고 복잡한 목차에서도 목표 회차를 빠르게 열고 원래 목록으로 돌아오게 한다.

**다섯째, 취향 기능과 기반 기능의 비용을 분리한다.**  
한 가지 효과를 넣으려고 전체 앱을 다시 작성하지 않는다. 반대로 현재 구조가 반복 구현을 양산한다면 ‘Vanilla라서 유지해야 한다’는 이유만으로 버티지도 않는다.

# 2. DESIGN.md를 원점에서 재판정

## 2.1 과거 거절의 맥락은 참고 자료이지 영구적인 취향 규칙이 아니다

기존 문서에는 2026년 7월의 거절 사유가 구체적으로 적혀 있다. 당시에는 따뜻한 배경, 보라색, 달 모양, 명조 UI, 반복 영문 표제, 큰 빈 표지가 **동시에** 사용됐고, 실제 글꼴 누락과 모바일 배치 문제도 있었다. 운영 화면에서는 넓은 회색 면, 과한 상태 장식, 옅은 설명, 상태 의미 혼동이 문제였다. [R2][R3]

이 기록으로부터 정당하게 도출할 수 있는 것은 ‘당시의 조합과 구현이 만족스럽지 않았다’는 점이다. **보라색·명조 제목·카드·종이색이 언제나 부적합하다는 결론까지 자동으로 따라오지는 않는다.**

현재 요청은 이 미적 선택을 다시 열어놓으라는 명시적인 지시다. 과거 문구를 사용자의 변하지 않는 선호로 취급하지 않는다.

### 접근성 규정도 ‘기존 문서에 적혔다’는 이유만으로 통과시키지 않는다

기존 DESIGN.md는 `light-subtle`을 일반 텍스트에는 부적합한 색으로 설명하면서 placeholder에는 사용할 수 있다고 적었다. 그러나 **활성 입력란의 placeholder도 원칙적으로 텍스트 대비 기준의 적용 대상**이다. 실제 비활성 컨트롤 등의 예외와, 입력란의 안내 문구를 혼동하면 안 된다. 따라서 이 규정은 그대로 유지할 것이 아니라 새 토큰·상태별로 다시 검사해야 한다. [R2][S7]

이 사례는 ‘미적 규정은 버리고 기술 규정은 그대로 믿는다’는 이분법도 충분하지 않음을 보여준다. 색·토큰·상태·실제 동작을 근거로 각각 검증한다.

## 2.3 새 디자인 원칙

‘금지 목록’ 대신 다음 질문으로 평가한다.

1. **식별:** 작품·회차·현재 위치·행동의 차이가 보이는가?
2. **연속성:** 설정 변경과 화면 이동 뒤에도 읽던 맥락이 유지되는가?
3. **선택권:** 개성 있는 서재와 조용한 본문을 독립적으로 선택할 수 있는가?
4. **진실성:** 보존 누락, 미열람, 분석 미완료, 원작 미완결을 섞지 않는가?
5. **비용:** 효과를 끄거나 로딩하지 않아도 핵심 기능이 완전한가?

이 원칙은 새로운 청록 테마나 표지형 UI에도 똑같이 적용한다. 과거 규정을 해체한 뒤 새로운 취향을 다시 영구적인 금지 규정으로 만들지 않는다.

| `search-core.js` | NFKC·소문자 정규화, 제목·작성자·분류 등의 검색 모델, AND/OR·정렬 계약 | 기존 검색을 ‘아무것도 없는 상태’로 취급하지 않는다. 정규화·정렬 계약을 새 엔진에서도 명시한다 [R8] |
| `app.js` 3035~3125 | 이전 요청 취소와 view ID 검사, 최초 진입 pushState·회차 이동 replaceState | 오래된 응답 방어와 Back 한 번 복귀 의미를 새 화면에서도 유지한다 [R9] |
| 제품 경험 문서 | Access/Worker/R2 Reader, 별도 Operations, 원문·revision과 stable ID의 구분 | 통합 서재를 만들더라도 원본 데이터와 인증 경계를 섞지 않는다 [R10] |

## 3.2 우선 해결할 구조적 문제

### A. ‘텍스트’는 자료 형태이지 사용자의 최종 목적이 아니다

소설을 찾는 사용자는 그것이 어떤 파이프라인에서 수집됐는지보다 작품명·연재 순서·읽던 위치를 먼저 원한다. 제안은 **소스 어댑터는 유지하고, 탐색과 Reader의 행동을 공통화**하는 것이다.

다만 제목이 같다는 이유만으로 다른 번역본·개정본·외전·다른 작가의 글을 하나로 합치지 않는다. 작품 묶기 알고리즘과 프론트 정보구조는 연결되지만 동일 과제가 아니다.

### B. ‘점진 렌더링’과 ‘DOM 개수가 제한되는 목록’은 다르다

현재 구조는 처음부터 전부 만들지는 않지만, 뒤로 갈수록 DOM이 누적될 수 있다. 특히 직접 회차 이동에서 앞부분까지 생성하는 경로를 우선 측정한다. **이것은 확인한 코드 구조이며, 실제 지연·메모리 수치는 아직 없다.** [R6]

### C. 위치 복원은 ‘대충 같은 퍼센트’보다 강해야 한다

기존 앵커를 버리지 않고 확장한다. 검색, 문장 기록, 각주 복귀, TTS, 버전 비교가 각자 다른 위치 체계를 만들지 않도록 **하나의 Reader locator**를 둔다.

### D. 화면 확장과 데이터 재작성은 분리해야 한다

표지·정규화 검색·인물 별칭·읽기 통계는 원문을 수정하는 이유가 아니다. 원문 보존 계층 위에 재생성 가능한 표시용/검색용 파생 데이터를 둔다.

# 5. 새 비주얼 방향: 네 가지 안과 최종 추천

## 5.1 방향 비교

아래 평가는 실험 결과가 아닌 디자인 제안이다.

| 방향 | 인상 | 적합한 과업 | 약점 | 추천 역할 |
|---|---|---|---|---|
| **A. 편집형 서재** | 책과 콘텐츠가 주인공인 현대적 편집 디자인. 중립적 따뜻한 면, 분명한 제목, 얇은 경계 | 소설 선택, 이어읽기, 장문 독서 | 잘못 만들면 다시 가짜 고서나 빈 여백 위주가 됨 | **기본 방향** |
| **B. 작품 중심 컬렉션** | 작품마다 표지·색·작은 패턴이 다른 수집형 서재 | 많은 작품의 시각적 식별, 개인 분류, 발췌 모음 | 표지 부족·무작위 색·큰 카드가 목록 밀도를 해칠 수 있음 | A 위의 선택적 작품 정체성 |
| **C. 떠 있는 읽기 도구** | 조용한 본문 위에 반투명 도크·작은 도구가 뜨는 방식 | 모바일 한 손 읽기, 집중 모드 | blur 대비·키보드·safe-area·제스처 충돌 | Reader 도구층에 제한적으로 |
| **D. 고밀도 아카이브 워크스페이스** | 표·목록·분할 패널 중심의 정확하고 빠른 화면 | 대형 장서 검색·목차 비교·버전 확인 | 소장감과 편안함이 약해질 수 있음 | 데스크톱 밀도 옵션·운영/분석 |

**최종 추천은 A를 기본으로, B의 작품 식별성과 C의 모바일 도구 배치를 선택적으로 결합하는 것이다.** D는 별도 밀도 모드로 제공한다. 네 가지 시각 스타일을 한 화면에 모두 섞지는 않는다.

기존 흰색/graphite/red도 폐기해야만 하는 것은 아니다. 새 방향의 **고대비 중립 프리셋**으로 남길 수 있다. 기본값을 바꾸는 것과 기존 사용자의 테마를 강제로 덮는 것은 다른 문제다.

## 5.2 화면마다 표현 강도를 다르게 한다

### 서재

표지·작품 제목·진행 상태가 눈에 남아야 한다. 카드 또는 작은 이미지가 있는 목록을 허용한다. ‘이어읽기’는 실제 작품과 회차가 보이는 한 개의 명확한 주행동으로 만든다. 검색은 항상 쉽게 접근할 수 있어야 하지만, 무조건 화면 최상단의 첫 픽셀이어야 한다는 식의 과거 규칙은 폐기한다.

### 작품 상세

작품명, 작가, 출처, 본문 유형, 보존 범위, 계속 읽기, 목차가 중심이다. 작품별 색과 짧은 시각 요소를 가장 적극적으로 쓸 수 있는 공간이다. 긴 줄거리·자동 생성 소개·거대한 히어로 영역을 기본으로 두지는 않는다.

### Reader

사용자가 고른 서체·폭·배경·문단 간격을 우선한다. 작품색은 회차 표시·진행선 등 작은 부분에만 적용하거나 완전히 끌 수 있게 한다. 도구가 닫히면 글과 AA가 남는다.

### 탐색·분석

본문과 분리된 패널 또는 페이지다. 그래프와 용어 색을 써도 되지만, 각 결과가 원문으로 연결돼야 한다. 분석을 열지 않은 사용자는 해당 코드·색인·차트를 내려받을 필요가 없어야 한다.

## 5.3 색상 초안

다음 값은 **구현 실험을 시작하기 위한 제안**이지 확정 브랜드 규격이 아니다.

| 역할 | 밝은 편집형 | 어두운 편집형 |
|---|---|---|
| 앱 배경 | `#F5F3EE` | `#121617` |
| 본문/떠 있는 면 | `#FFFEFB` | `#1C2223` |
| 주 텍스트 | `#24272C` | `#E8EDEB` |
| 보조 텍스트 | `#60666D` | `#ADB8B3` |
| 강조 | `#236B63` | `#89D6C5` |
| 밝은 모드 연한 강조 면 | `#E3F0EC` | 별도 조정 |

sRGB 상대 휘도 공식으로 **불투명 단색 조합만** 계산한 대비는 밝은 본문 14.86:1, 밝은 보조 5.75:1, 밝은 강조 6.21:1, 연한 강조 면 위 강조 5.35:1이다. 어두운 면의 본문 13.62:1, 보조 7.90:1, 강조 9.59:1이다. 이는 전체 앱 접근성 합격을 의미하지 않는다. 투명도·disabled·hover·사진 위 글자·실제 크기는 별도 검사한다. [S7]

초록 계열을 추천하는 이유는 기존 red 신호와 오류색의 역할을 분리하고 새 서재의 인상을 비교하기 쉽기 때문이다. **청록색이 독서에 과학적으로 더 좋다는 주장은 아니다.** 청록·indigo·기존 red 세 안을 같은 실제 작품 데이터로 비교하면 된다.

## 5.4 표지가 없는 작품을 예쁘게 만드는 방법

우선순위는 **실제 표지 → 사용자가 지정한 이미지 → 타이포그래피 카드 → 텍스트 목록**이다.

타이포그래피 카드는 작품명·작가·짧은 부제·작품에 고정된 색/패턴을 활용한다. 원본 표지처럼 위장하지 않는다. 같은 작품은 목록 정렬·새로고침·제목 정정으로 색이 매번 바뀌지 않도록 stable work ID 기반 선택을 저장한다.

권장 크기는 전체 목록에서 큰 포스터보다 **작은 작품 식별 영역**이다. 카드형은 ‘이어읽기·즐겨찾기·개인 서재’에서 특히 유용하고, 수천 개 전체 목록은 컴팩트 모드를 유지한다.

사용자가 별도 지정하지 않은 경우, 미래 회차의 반전 이미지나 인물 이름을 자동으로 대표 이미지·태그로 추출하지 않는다. 개인 지정 표지의 출처와 원본 표지의 출처를 별도 필드로 보관한다.

## 5.5 테마를 두 축으로 분리한다

- **앱 테마:** 중립/편집형/작품색, 밝음/어둠/시스템.
- **읽기 프로필:** 흰색/종이/회색/검정, 서체·폭·행간·문단 간격.
- **AA 프로필:** 폰트·크기·가로 위치·배경·원본색/정규화색.

예를 들어 앱은 청록 편집형이어도 본문은 흰색 산세리프, AA는 원본색 보존일 수 있다. 테마를 바꿨다고 AA의 색 의미나 맞춤 폭이 바뀌지 않아야 한다.


# 6. 정보구조와 실제 화면 동선

## 6.1 추천 정보구조

```text
내 서재
├─ 이어읽기
├─ 고정한 작품 / 나의 분류
├─ 스마트 서재
└─ 최근 보존 / 최근 읽음

둘러보기
├─ 작품 중심 보기
├─ 게시판·출처 중심 보기
└─ 목록 / 카드 / 컴팩트 밀도

검색
├─ 제목·작가·분류
├─ 작품 본문
└─ 표시한 문장·내 메모

기록
├─ 저장한 작품·글
├─ 발췌·메모
└─ 읽기 이력

작품
├─ 작품 정보·보존 범위
├─ 목차·회차 지도
├─ 계속 읽기
└─ 작품에서 찾기 / 선택적 작품 탐색

Reader
├─ 본문: 산문 / AA / 혼합
├─ 목록·이전·다음
├─ 찾기·문장 기록·각주·댓글
└─ 읽기 설정

설정·운영
└─ 계정 / 기록 백업 / 기기 저장 / 운영 상태
```

이것은 메뉴를 한 번에 전부 추가하라는 뜻이 아니다. 처음에는 현재 홈·검색·보관함을 재배치하고, 없는 기능은 숨긴다. 현재 메뉴의 기술적인 ‘텍스트’ 구분은 **출처/자료유형 필터와 어댑터 내부 구분**으로 옮기는 안을 우선 검토한다.

작품 연결이 아직 불확실한 자료는 별도 글로 남긴다. UI 공통화를 위해 자동 묶기 확신도를 과장하지 않는다.

## 6.2 모바일: 한 손 사용을 독립 요구사항으로 본다

과거 사용 맥락인 Galaxy 계열 Android·한 손 조작을 기준으로 설계하되, 실제 대상 기기와 브라우저 버전은 구현 검증 시 다시 기록한다. 픽셀 폭을 특정 기종의 물리 해상도와 혼동하지 않는다.

**전역 화면:** 내 서재 / 둘러보기 / 검색 / 기록을 하단에서 접근한다. 설정과 운영은 보조 진입점으로 둔다.

**Reader:** 전역 메뉴를 숨기고 `목록 · 이전 · 다음 · 찾기 · 설정`을 기본 후보로 둔다. 문장 저장은 선택 메뉴, 글 저장은 제목 옆 또는 설정 가능한 도구 슬롯에서 접근한다. 기존 버튼 배치를 절대 규칙으로 유지하지 않고 실제 반복 사용 빈도로 비교한다.

중요한 조건은 다음과 같다.

- 이전·다음·목록은 기본 화면에서 직접 접근한다.
- 게시판 바꾸기를 작은 화면이라는 이유로 삭제하지 않는다.
- 아이콘만 보고 추측하지 않도록 주요 행동에 짧은 한국어 label을 둔다.
- 설정·검색·문장 선택 중에는 자동 숨김을 멈춘다.
- 시스템 뒤로가기와 좌우/세로 제스처를 빼앗는 전면 gesture handler를 기본으로 쓰지 않는다.
- 검색 키보드가 올라왔을 때 결과와 닫기/복귀 행동이 실제 보이는 영역 안에 남아야 한다.
- 긴 메뉴는 상단 작은 팝오버보다 충분한 높이의 시트 또는 독립 화면을 사용한다.

주요 조작부의 **44 CSS px 이상 터치 영역을 초기 제품 목표**로 잡는다. 이것을 WCAG 2.2 AA의 일률적인 숫자 기준이라고 쓰면 안 된다. 해당 최소 기준은 24×24 CSS px 또는 규정된 예외·간격 조건이며, 제품에서는 한 손 조작을 위해 더 여유 있게 잡는 것이다. [S8]

## 6.3 데스크톱: 항상 세 칸일 필요는 없다

기본은 목록+Reader 두 면이다. 작품 검색·문장 기록을 열었을 때만 보조 패널을 추가한다. 읽기 폭이 부족하면 목차를 접거나 검색을 overlay로 전환한다.

여러 패널을 켠 경우 사용자 폭 조절을 허용하되, 본문 폭 하한과 패널 접기를 함께 제공한다. 화면이 넓다고 문장을 끝없이 늘이지 않는다. AA는 산문과 다르게 넓은 stage를 사용할 수 있다.

분석·버전 비교처럼 넓은 공간이 필요한 작업은 별도 작업 면으로 분리한다. 작은 Reader 오른쪽 패널에 거대한 관계도를 억지로 넣지 않는다.

## 6.4 Back과 ‘원래 자리’ 계약

기존 코드는 Reader 최초 진입에 히스토리를 추가하고 회차 이동은 교체한다. 이 의미는 유지한다. [R9]

다만 모든 보조 패널에 무조건 `pushState`를 추가하면 새 UI가 기존 계약을 깨뜨릴 수 있다. 아래 상태를 따로 모델링한다.

```text
entryContext: 어디서 Reader에 들어왔는가
readingLocator: 현재 실제 읽는 위치
toolContext: 검색어·결과 선택·메모 편집 등 도구 상태
returnLocator: 각주/검색/미리보기 이전 위치
```

검색 결과를 미리 봤다가 돌아오는 것은 읽기 진도를 임의로 갱신하지 않는다. Android Back, 브라우저 Back, 화면의 목록 버튼, 검색 결과 복귀 버튼을 각각 테스트한다. **보조 도구 닫기와 원래 목록 복귀를 구별하되, 회차 이동 수만큼 Back을 요구하지 않는다.**

## 6.5 화면 상태도 디자인에 포함한다

정상 화면만 예쁘게 만들지 않는다. `불러오는 중`, `현재 범위 결과 없음`, `미보존`, `색인 미생성`, `인증 만료`, `오프라인`, `이미지 링크 만료`, `기록 저장 실패`를 서로 다른 상태로 설계한다.

단계별 로딩 상태를 표지 placeholder 문구 하나로 치환하지 않는다. 색인 로딩 중 결과 0을 보여주거나, 미보존을 원작 미완결로 표현하지 않는다. 오류 원인·영향 범위·가능한 다음 행동이 짧게 보여야 한다.

# 7. 한국어 조판과 서체: 이번에 더 깊게 다뤄야 할 영역

## 7.1 서체 선택은 역할별로 비교한다

| 역할 | 후보 | 비교할 지점 | 권장 방향 |
|---|---|---|---|
| UI·작품 목록 | 현재 SUIT / Pretendard / Wanted Sans | 좁은 화면의 긴 한국어 제목, 숫자·한자·영문 혼용, 중간 굵기, 실제 로딩 | 기존 SUIT를 대조군으로 두고 하나만 주 UI 서체로 선택 |
| 한국어 산문 | 현재 MaruBuri / 리디바탕 / UI 산세리프 | 작은 크기의 획·속공간, 대사와 긴 문단, 읽기 선호, 실제 fallback | 명조/고딕 선택권 유지. 명조끼리의 추가 선택은 지연 로드 |
| 일본어·한자 혼합 | 해당 글리프를 가진 fallback | 한자만 다른 폰트로 튀는지, ruby·구두점·baseline | 글리프 범위와 테스트 자료를 먼저 확인 |
| AA | 현재 Saitamaar / 자료 유형에 맞는 호환 후보 | 개별 문자 폭·공백·개행·색상·특수문자 정렬 | 일반 본문 서체와 분리 |

Pretendard는 동적 서브셋과 가변 폰트 배포 방법을 제공하고, Wanted Sans 역시 가변 폰트 후보가 된다. 리디바탕은 공식 배포와 OFL 라이선스를 확인할 수 있다. 이 사실만으로 현재 SUIT/MaruBuri보다 반드시 낫다고 판단하지 않는다. [S4][S9][S10]

### 실제 비교 방법

같은 8개 fixture를 동일 크기와 폭으로 렌더링한다. 긴 제목, 한국어 대사, 한자 인명, 영문 약어, 숫자, 괄호·말줄임표, 작은 주석, 특수문자를 포함한다. ‘폰트가 새로워 보인다’뿐 아니라 **몇 번 줄바꿈되는지, 클릭 영역을 침범하는지, 설정 변경 후 같은 문장으로 돌아오는지**를 본다.

독서 서체 선택 화면에는 폰트 이름만 나열하지 않고 현재 원문의 짧은 구간으로 미리보기를 제공한다. 선택하지 않은 본문 서체 전부를 시작 시 내려받지 않는다.

## 7.2 한국어에 맞는 줄바꿈

제목·버튼에는 `word-break: keep-all`이 유용할 수 있지만, 긴 산문 전체에 강제하면 좁은 화면에서 큰 빈칸과 불균형한 줄이 생길 수 있다. 본문은 기본적인 한국어 줄바꿈을 대조군으로 두고 사용자가 조정할 수 있게 한다.

행 길이를 영어의 `ch` 숫자 하나로 결정하지 않는다. `ch`는 ‘한글 한 글자 폭’이 아니다. `ic` 같은 CJK 관련 단위와 실제 폰트 폭을 후보로 검토하되, 지원·fallback·실측을 함께 확인한다. [S6][S11]

초기 제안값은 모바일 본문 18px 전후, 행간 1.65~1.9, 좌우 여백 18~24px 범위다. 이는 최적값을 입증한 결과가 아니라 **실제 사용자 설정으로 조정할 시작점**이다. 글자 크기·행간·문단 간격·폭을 서로 독립적으로 조절한다.

## 7.3 원본 문단과 보기용 재흐름을 분리한다

TXT에는 문단 구분과 강제 개행이 섞일 수 있다. 모든 줄바꿈을 문단으로 만들거나, 반대로 모든 줄바꿈을 제거하면 문체와 대사 표현을 바꿀 수 있다.

권장 정책은 다음이다.

- 기본은 원본의 의미 있는 문단·개행 보존.
- 수집 단계에서 확실한 문단 구조를 얻은 경우에만 그 구조를 사용.
- 긴 TXT의 줄 감김 복원은 별도 보기 옵션으로 제공하고 원본 보기로 되돌릴 수 있게 함.
- AA·시·코드·표·일부 대화형 게시물에는 산문 재흐름을 자동 적용하지 않음.
- 검색용 정규화와 화면 표시용 재흐름을 같은 함수로 처리하지 않음.

일본어 ruby가 원문에 있다면 유지하는 방식을 검토한다. 원문에 없는 독음·화자·장면 경계를 자동 생성해 원문 정보처럼 보이게 하지 않는다.

## 7.4 글꼴 성능은 ‘종류 수 금지’보다 로드 정책으로 관리한다

기본 UI, 현재 선택한 본문, 필요한 AA만 우선 로드한다. 문자 subset을 쓰더라도 드문 한자·기호·혼합 언어가 빠졌을 때 fallback이 AA를 깨뜨리지 않는지 확인한다.

폰트 변경은 사용자 행동 한 번에 대응하도록 처리하고, 글꼴 로딩·화면 회전·이미지 지연 로딩이 겹쳐 스크롤 보정이 반복 진동하지 않게 한다. **한글 글꼴이 완료되기 전과 후의 위치 안정성도 Reader 품질**이다.

# 8. AA·이미지·혼합 게시글에 맞는 뷰어

## 8.1 ReDSTM은 일반 소설 뷰어만이 아니다

산문, AA, 이미지, 댓글, 원문색, 특수문자, 링크가 섞인다. 따라서 ‘모든 콘텐츠를 동일한 텍스트 렌더러에 넣는 것’보다 다음처럼 모드를 분리하는 편이 적절하다.

| 콘텐츠 | 렌더링 원칙 | 주요 도구 |
|---|---|---|
| 한국어 산문 | 가변 폭·사용자 서체·문단 조절 | 찾기, 표시, 각주, 선택적 TTS |
| AA | 문자 배치·공백·행·폰트 지표 보존 | 맞춤/원배율, 확대, 가로 위치 복원 |
| 산문+AA 혼합 | 가능한 경우 신뢰할 수 있는 원본 블록 경계 활용 | 블록별 모드, 전체 원문 보기 |
| 일반 이미지 | 가로세로 크기 예약·안전한 확대 | 개별 확대, 이미지 목록 |
| 매우 긴 이미지 | 길이를 고려한 스크롤·분할 로드 전략 | 별도 세로 보기, 일반 lightbox와 구별 |
| 댓글/부가정보 | 원문과 별도 출처·순서·정체성 | 접기, 댓글로 이동, 본문 복귀 |

블록 판정이 불확실한 혼합 글을 휴리스틱 하나로 잘라 다시 조판하지 않는다. **원본 보기로 돌아갈 수 있는 가역적인 표현 계층**을 우선한다.

## 8.2 AA에서 중요한 것은 등폭 여부가 아니라 실제 문자 지표다

고전 Mona Font는 공식 설명부터 일본식 텍스트 아트를 위한 proportional font다. 터미널 열 폭을 계산하는 논리와 브라우저에서 AA를 그리는 논리를 같게 취급하면 안 된다. [S12]

현재 Saitamaar를 유지하는 가장 강한 이유는 과거 규칙이 아니라 **실제 보유 AA와의 호환성을 이미 기준으로 삼을 수 있다는 점**이다. 교체를 금지하지는 않되 golden sample 비교를 통과해야 한다. [S13]

추천 개선은 다음과 같다.

- ‘화면에 맞춤’과 ‘원래 크기’를 명확히 구분한다.
- 확대했을 때 문서 전체가 아니라 AA 영역의 가로 위치를 안정적으로 관리한다.
- 처음부터 아주 작은 글씨로 축소하기보다 맞춤 결과가 읽기 어려우면 확대 가능한 상태임을 안내한다.
- 가로로 더 볼 수 있다는 표시를 첫 진입 때만 가볍게 제공한다.
- 원본색·단색 보기의 의미를 짧게 설명하고 개별 작품에 선택값을 기억할 수 있게 한다.
- 원문 복사와 텍스트 선택을 확대/드래그 제스처가 막지 않게 한다.
- AA의 전각/반각·공백·개행에 NFKC·Markdown 처리를 적용하지 않는다.

**장면 단위 AA 보기**는 실험 가치가 있다. 다만 원본의 게시글/블록 경계가 명확할 때만 이동 단위로 사용한다. 빈 줄 개수만으로 장면을 확정하거나 텍스트를 그림으로 바꿔버리는 방식은 기본으로 삼지 않는다.

## 8.3 이미지 확대는 기존 구현을 비교 대상으로 놓는다

PhotoSwipe는 일반 이미지 확대와 gallery를 위한 좋은 비교 후보이고, Panzoom은 확대·이동 제어의 후보가 된다. 그러나 이미 있는 이미지 뷰어를 교체한다고 자동으로 좋아지지는 않는다. [S14][S15]

PhotoSwipe는 이미지 크기 정보를 필요로 하며, 공식 문서도 초대형 이미지 전용 도구는 아니라고 설명한다. 따라서 매우 긴 게시글 이미지와 AA stage까지 하나의 PhotoSwipe 안에 넣는 방향은 피한다. [S14]

만료 URL·차단 이미지·미보존 이미지에서 임의 placeholder로 조용히 바꾸지 않는다. ‘원문 링크를 다시 확인해야 함’과 ‘보존된 이미지 없음’을 구분한다. 그림이 늦게 표시될 때 현재 읽는 문장이 아래로 밀리지 않도록 크기 예약과 locator 복원을 함께 사용한다.

## 8.4 미디어 탐색이라는 추가 기능

이미지가 많은 게시글에서는 ‘이 글의 이미지’ 목록을 보조 패널로 제공할 수 있다. 선택하면 원문의 위치로 돌아간다. 로컬에 보존되지 않은 이미지는 썸네일이 있는 것처럼 가장하지 않는다.

AA도 사용자가 직접 표시한 장면에 한해 ‘장면 책갈피’를 둘 수 있다. 자동으로 미래 장면을 대표 이미지로 뽑아주는 기능보다 스포일러와 원문 위치 관리가 단순하다.

# 9. 제품에 잘 맞는 기능 제안: 우선순위와 구현 범위

## 9.1 스마트 서재 — 기존 수동 분류의 확장

이미 있는 수동 분류를 없애지 않는다. 사용자가 고른 조건으로 자동 갱신되는 **저장된 보기**를 추가한다. Readwise의 필터 뷰가 유용한 제품 레퍼런스다. [R6][S1]

예시:

```text
계속 읽을 것: 읽는 중 AND 사용자가 지정한 분류
새 보존분: 즐겨찾기 작품 AND 마지막 확인 이후 새 회차가 보존됨
짧게 읽을 것: 확인된 분량 범위 AND 미열람
다시 볼 문장: 표시한 문장이 있는 작품
AA 모음: AA 자료 AND 사용자 지정 태그
```

‘새 보존분’과 ‘원작 새 연재’를 구분한다. 분량 미측정 자료를 짧은 작품으로 취급하지 않는다. 조건에 없는 사용자의 성향을 추정하는 추천 시스템은 필요하지 않다.

**우선순위: 높음.** 현재 메타데이터로 만들 수 있고 본문 분석이 없어도 유용하다.

## 9.2 재진입 카드 — ‘지난번 어디까지 읽었지?’

이어읽기에 작품명·회차·마지막 읽은 시각·짧은 직전 원문을 보여준다. 사용자가 표시한 메모가 있다면 함께 볼 수 있게 한다.

‘요약’이라고 쓰면서 임의로 새 줄거리를 생성하지 않는다. 초기 버전은 **직전에 실제로 본 원문 발췌**만 사용하면 된다. 잠금 화면이나 공용 화면에서 민감한 발췌가 보이지 않도록 표시를 끌 수 있게 한다.

한 작품의 먼 회차를 잠깐 미리 본 경우 이어읽기를 그 위치로 덮지 않도록 `읽기`와 `미리보기` 진입을 구분한다.

**우선순위: 높음.** 보관 중심 서비스의 반복 재방문에서 체감 가치가 크다는 설계 판단이다.

## 9.3 현재 회차 찾기 → 작품 검색 → KWIC

찾기를 누르면 기본 검색 범위를 분명히 표시한다. 결과 개수·이전/다음 일치·현재 결과 강조를 제공한다. 작품 전체로 넓혔을 때는 회차별 문맥과 실제 원문 위치로 이동한다.

강조에는 CSS Custom Highlight API를 우선 검토한다. 텍스트를 수많은 span으로 감싸지 않는 방식이지만, 결과 목록·키보드·접근성·영속 저장은 별도로 구현해야 한다. [S16]

미지원 환경도 결과 목록과 문단 이동으로 기능을 유지한다. 브라우저 지원표 하나만 보고 모든 Android 브라우저에서 같다고 가정하지 않는다.

**우선순위: 매우 높음.** 새 검색 엔진과 관계없이 현재 회차 찾기부터 독립 완결할 수 있다.

## 9.4 문장 표시·메모·발췌함

문장 선택 뒤 `표시 / 메모 / 복사`를 제공한다. 범위 선택을 기준으로 도구 위치를 계산하는 Floating UI DOM이 후보가 된다. 모바일 기본 텍스트 선택 메뉴를 방해하지 않는지가 더 중요하다. [S17]

저장되는 것은 색만이 아니다. 원문, 작품·회차, 작성한 메모, 위치 정보, 원문 버전이 함께 있어야 한다. 원문이 바뀌어 위치를 못 찾더라도 발췌와 메모는 남는다.

Rough Notation은 저장된 발췌 카드의 손그림 밑줄처럼 **개인 기록의 표현**에 잘 맞을 수 있다. 위치 저장 엔진과 섞지 않는다.

**우선순위: 높음.** locator와 사용자 데이터 저장 설계가 선행한다.

## 9.5 회차 지도·진행 탐색

읽은 회차, 현재 회차, 미열람, 보존 누락을 지도 형태로 압축한다. 검색어 위치·메모 위치는 별도 모드다. 1,000개의 작은 터치 버튼을 그리는 대신 구간을 확대해 세부 회차를 선택한다.

긴 작품에는 다음 미열람 구간, 현재 회차 근처, 번호 직접 이동을 함께 제공한다. 번호와 실제 정렬 인덱스, 외전/후기/프롤로그를 구분한다.

**우선순위: 높음~중간.** 현재 읽기 상태만으로 1차 버전이 가능하다.

## 9.6 각주·주석·댓글의 안전한 왕복

원문 각주 링크는 작은 미리보기 또는 보조 패널에서 읽고 원래 문장으로 돌아온다. 원문 주석, 댓글, 내 메모를 서로 다른 종류로 표시한다.

댓글 수가 많으면 본문 전체를 끝까지 내려가야만 댓글을 볼 수 있는 구조를 개선한다. 다만 현재 회차만 읽었는데 미래 회차를 다루는 댓글이 기본으로 노출되지 않도록 사용자의 펼침 행동을 우선한다.

**우선순위: 중간.** 수집본의 실제 링크/댓글 구조를 확인한 뒤 적용한다.

## 9.7 작품별 이름·별칭 사전

한국어 팬픽은 같은 이름의 번역 표기·별칭·성/이름 순서가 달라질 수 있다. 처음부터 거대한 지식 그래프보다 사용자가 편집 가능한 작은 별칭 사전이 유용하다.

예를 들어 작품 내 `린`과 `Rin`을 연결할 수 있지만, 모든 작품의 ‘린’을 같은 인물로 통합하지 않는다. 별칭이 미래 반전을 포함하면 읽은 범위에 따라 공개 여부를 관리한다.

사전의 정의는 원문 인용·사용자 메모·자동 추정 중 무엇인지 표시한다. 자동 추정을 사실로 승격하지 않는다.

**우선순위: 중간.** 검색과 KWIC가 먼저다.

## 9.8 보존본 변경 보기·버전 비교

아카이브의 성격에 잘 맞는 차별 기능이다. ‘지난 보존본과 무엇이 달라졌나’를 글/문단 단위로 보여준다. 제목·본문·이미지 상태·댓글 변경을 구별한다.

초기에는 버전 메타데이터와 변경 블록 요약으로 시작한다. 문자열 diff만으로 두 버전의 문단 대응을 확정하지 않는다. AA는 문자 삽입 강조가 배치를 망칠 수 있으므로 원본 나란히 보기 또는 변경 블록 단위 비교가 더 적절할 수 있다.

번역본 대조도 동일한 방식의 확장 후보지만, 원문/번역본 관계가 검증된 자료만 연결한다. 제목 유사도로 자동 병합하지 않는다.

**우선순위: 중간~후순위.** 보존본 가용성과 블록 대응이 전제다.

## 9.9 선택적 오프라인 읽기

작품 전체 자동 다운로드가 아니라 ‘이후 몇 회차를 이 기기에 저장’처럼 범위를 명시한다. 다운로드 크기·이미지 포함 여부·보존본 시각·삭제를 보여준다.

인증이 만료돼도 오프라인 본문을 볼 수 있게 할 것인지 먼저 결정해야 한다. 이는 단순 캐싱 옵션이 아니라 개인정보 정책과 사용자 기대의 문제다. 14장에서 별도로 다룬다.

**우선순위: 중간.** 실제 이동 중 읽기 요구가 확인되면 시각화보다 앞당길 수 있다.

## 9.10 한국어 읽어주기(TTS)

산문 전용 보조 기능으로 검토한다. 재생/일시정지, 문장 이동, 속도, 타이머, 현재 문장 표시부터 시작한다. AA의 기호를 전부 발음하거나 원문에 없는 화자를 자동 연기하지 않는다.

웹 음성은 기기·브라우저·설치된 음성에 따라 달라진다. `SpeechSynthesisVoice.localService`로 로컬 음성인지 구분할 수 있지만, 이 정보만으로 실제 개인정보 흐름 전체를 보증하지 않는다. 외부 음성 엔진을 사용하는 경우 사용자 동의와 전송 범위가 필요하다. [S18]

RIDI 모바일 앱의 TTS는 레퍼런스이지 ReDSTM 웹에서 잠금 화면·백그라운드·자동 회차 연속 재생을 보장한다는 근거가 아니다. 실제 기기 검증 전에는 기능 범위를 과장하지 않는다. [S3]

**우선순위: 선택.** 한글 독서와 직접 관련되지만 기본 Reader의 정확도를 앞서지는 않는다.

## 9.11 작게 추가해도 좋은 편의 기능

| 기능 | 실제 가치 | 주의점 |
|---|---|---|
| 키보드 단축키 안내·명령 검색 | 데스크톱의 회차 이동·설정 접근 | 입력 중·IME 조합 중 단축키를 실행하지 않음 |
| 읽기 프로필 | 산문·AA·작품별 설정 반복 감소 | 전체 기본값과 작품 예외를 구분 |
| 빠른 ‘이 위치 기억’ | 검색·각주·목차 왕복 | 정식 읽기 위치와 별도 임시 포인터 |
| 메모 검색 | 저장한 문장 재발견 | 원문 검색과 내 메모 검색 범위 표시 |
| 외부 링크 미리 알림 | 원문·외부 사이트로 빠져나가는 실수 감소 | 모든 링크를 무조건 modal로 막지 않음 |
| 선택적 조용한 완료 표시 | 회차 끝 도달 피드백 | 실제 이해도·완독을 단정하지 않음 |
| 데이터 품질 표시 | 보존 누락·이미지 상태 파악 | 기술 해시를 제목보다 크게 노출하지 않음 |
| 필터 조건 요약·초기화 | ‘왜 결과가 없지?’ 해결 | 숨은 source/language 필터 방지 |
| 제목 펼치기 | 긴 웹소설 제목 식별 | marquee 자동 스크롤보다 사용자가 펼침 |

이 목록을 한 번에 모두 구현하지 않는다. 작품을 찾고 읽는 실제 동선의 장애를 먼저 해결한다.

# 10. 한국어 검색: 라이브러리보다 먼저 정의할 계약

## 10.1 검색 모드를 한 덩어리로 만들지 않는다

| 모드 | 목적 | 기본 동작 |
|---|---|---|
| 정확한 문구 | 기억나는 대사·특수한 표현 찾기 | 원문에 실제 있는 연속 문자열을 찾음 |
| 편한 문구 | 띄어쓰기·전각/반각 차이 보완 | 정규화 사본에서 찾고 원문으로 정밀 매핑 |
| 제목·작가 탐색 | 작품 재발견 | 정확 일치·부분 일치 우선, 초성은 별도 경로 |
| 유사 검색 | 오타 보완 | ‘유사한 결과’로 분리. 정확 결과를 조용히 치환하지 않음 |
| 작품 용어 검색 | 이름·장소·설정 찾기 | 작품별 별칭과 필요 시 형태소 분석 활용 |
| 내 기록 검색 | 메모·발췌 찾기 | 사용자 데이터 인덱스에서 검색 |

현재 metadata 검색에는 NFKC 정규화가 이미 있다. 새 기능의 의미는 ‘정규화를 처음 넣는다’가 아니라 **검색 목적별 정책과 원문 위치 대응을 명확히 한다**는 것이다. [R8]

## 10.2 한국어 도구의 역할 분담

### es-hangul

초성 추출, 한글 분해/조합, 조사 처리 등 UI·검색 보조 도구다. 작품명 초성 인덱스, 자연스러운 한국어 메시지 등에 적합하다. **형태소 분석기나 전체 검색 엔진이 아니다.** [S19]

초성 검색은 제목·작가·사용자 태그처럼 짧은 필드에 먼저 적용한다. 모든 본문 문장을 초성으로 변환해 검색하면 충돌과 색인 비용이 커지므로 기본으로 넣지 않는다.

### Intl.Segmenter

문자군·단어·문장 단위를 나누는 플랫폼 API다. 선택 범위, 문장 단위 TTS, snippet 경계에 후보가 된다. **한국어 조사·어미·고유명사를 정확히 분석하는 형태소 엔진과 동의어가 아니다.** [S20]

### Kiwi / kiwipiepy

한국어 형태소·문장 분석과 사용자 사전이 필요한 경우 배치 처리 후보다. 작품의 고유명사·외래어를 사전에 추가할 수 있지만, 별칭 연결과 등장인물 동일성까지 자동 해결하는 것은 아니다. [S21]

추천 실행 위치는 **원문에서 파생 데이터를 만드는 별도 배치 단계**다. 모든 모바일 기기에서 모델을 로드하거나, 수집 작업의 메모리가 제한된 서버에서 무제한 병렬로 돌리는 구성을 기본으로 잡지 않는다. 실제 코퍼스에서 사전·모델·실행 시간·메모리를 재야 한다.

## 10.3 검색 엔진 비교

| 후보 | 확인한 특징 | ReDSTM에 맞는 위치 | 핵심 검증 |
|---|---|---|---|
| 직접 문자열 검색 | 현재 회차의 DOM/원문 모델에서 제어 가능 | 현재 회차 찾기의 기본 | 여러 text node·정규화·반복 문장·한 글자 |
| **MiniSearch** | 메모리 내 전문 검색, 필드 가중치·prefix·fuzzy·사용자 tokenizer | 작품별 또는 제한된 범위의 본문 검색 | 임의 중간 문자열 검색과 다름. 한국어 tokenizer·메모리 [S22] |
| **FlexSearch** | encoder 설정과 CJK 처리, 사용자 처리 경로 | 한국어·혼합 텍스트 성능 비교군 | 기본 dedupe·기호 제외가 작품명/의성어를 훼손하지 않는지 [S23] |
| **Pagefind** | 빌드 시 정적 색인, 한국어 분절, 비HTML custom record API | 정적 보존본 기반 장서 검색의 유력 후보 | 검색 품질·색인 크기·release 배포·원문 locator 연결 [S24][S25] |
| **Fuse.js** | fuzzy·가중 필드·확장 검색 등 | 작은 카탈로그·태그·명령·유사 제목 제안 | 대규모 본문 도입은 실제 데이터 측정 후. 최신 문서의 beta 기능 혼동 주의 [S26] |
| **Orama** | 공식 tokenizer README에 한국어를 experimental로 표시 | 장기 비교군 | 한국어 미지원으로 단정하지 않음. 실제 설치할 릴리즈의 export·의존성·정확도는 별도 검증 [S27] |
| **SQLite FTS5** | 일반 전문 검색 및 trigram tokenizer | 별도 인증 검색 API를 둘 때의 후보 | 한국어 형태소 분석과 동일하지 않음. 짧은 query와 운영 환경 지원 확인 [S28] |

### 이번 조사에서 중요한 수정: Pagefind를 제외할 이유가 없다

Pagefind 공식 문서는 한국어 UI와 분절 지원을 구분해 설명하며, 한국어 stemming은 지원하지 않는 것으로 표시한다. Node API의 `addCustomRecord`를 사용하면 HTML 파일을 공개 페이지로 전부 만들지 않고도 본문 레코드로 색인을 만들 수 있다. [S24][S25]

따라서 ReDSTM의 정적 보존본 구조에서는 충분히 비교할 가치가 있다. 다만 `custom record → 검색 결과 → 원문 문장` 연결을 별도로 설계해야 하며, 색인 파일까지 반드시 같은 인증 경계 안에서 제공해야 한다.

### FlexSearch에서는 정확성 옵션을 먼저 본다

공식 encoder 문서는 기본 연속 문자 중복 제거, 기호 제외 등을 설명한다. 이런 처리와 한국어의 반복 의성어·작품명 기호·버전 표기는 충돌할 수 있다. CJK 설정이 있다는 이유만으로 기본값을 그대로 최적이라고 간주하지 않는다. [S23]

### FTS5에서는 짧은 검색어를 놓치지 않는다

trigram 전문 검색은 3자 미만의 검색 문자열에 제약이 있다. ‘린’, ‘검’, ‘서울’처럼 짧은 질의를 위한 별도 경로가 필요하다. 일반 SQLite에서 가능한 구성이 현재 Worker/D1 배포에서도 그대로 가능한지는 별도 확인 대상이다. [S28]

## 10.4 최종 추천 배치

```text
제목·작가·태그
  → 기존 정확 검색 유지 + es-hangul 초성 + 선택적 유사 결과

현재 회차
  → 원문 text model의 정확/편한 문구 검색 + Highlight

작품별 본문
  → MiniSearch와 FlexSearch를 동일 한국어 fixture로 비교

전체 정적 장서
  → Pagefind와 작품별 shard 구성을 비교
  → 초기에 모든 본문을 한 브라우저 메모리로 적재하지 않음

형태소·분포·별칭 보조 데이터
  → 필요할 때 Kiwi 배치 + 사용자 사전
```

**출시 앱에 검색 엔진 세 개를 모두 넣자는 제안이 아니다.** 비교 실험을 거쳐 작품별 엔진을 하나 고르고, 전체 장서 검색이 실제 필요할 때 별도 경계를 추가한다. 작은 자료 규모에서는 기존 검색+직접 문자열 검색이 더 경제적일 수 있다.

## 10.5 정확한 위치 매핑

정규화 문자열의 offset을 원문 DOM에 그대로 적용하지 않는다. NFKC, 공백 압축, 한글 분해, 문장 분리, 형태소 분석은 길이와 경계를 바꿀 수 있다.

서버의 Python 문자 offset, JavaScript의 UTF-16 offset, 사용자가 보는 문자군은 동일하지 않다. 다음 원칙을 둔다.

- 원문 텍스트와 검색용 사본을 따로 저장한다.
- 검색 색인의 위치는 원문 block ID와 원문 구간으로 다시 연결한다.
- 정규화는 구간 대응표를 만들고 일대다·다대일 변환을 허용한다.
- 같은 문구의 모든 후보를 찾은 뒤 앞뒤 문맥과 revision으로 검증한다.
- 불확실한 위치는 ‘가까운 문단’ 또는 ‘위치 미확인’으로 표시하고 정확한 위치인 것처럼 조용히 이동하지 않는다.

## 10.6 한국어 검색 검증 세트

아래는 **검증용 예시**이며 실제 보유 작품이나 실제 측정 결과가 아니다.

| 테스트 | 기대 |
|---|---|
| `붉은 기록` / `붉은기록` | 정확 검색과 공백 허용 검색의 결과 차이가 명확함 |
| `ㅂㅇ ㄱㄹ` | 초성 제목 탐색에서 후보를 찾되 모든 본문까지 자동 확장하지 않음 |
| `도서관` / `도서관에서` | literal·token 검색의 의미가 구분되고 기존 부분 일치가 사라지지 않음 |
| `린` / `Rin` | 사용자가 등록한 해당 작품의 별칭에서만 연결 |
| `검`, `서울` | 1~2글자 질의가 무조건 0건이 되지 않음 |
| `ㅋㅋㅋㅋ`, `하하하` | 정확 검색에서 반복 수를 몰래 축약하지 않음 |
| `Fate/stay night`, `A+B`, `1.5부` | 기호 제거 정책 때문에 다른 제목과 합쳐지지 않음 |
| `ＡＢＣ` / `ABC` | 편한 검색은 연결할 수 있으나 원문 표시는 보존 |
| 같은 `알겠어.`가 여러 번 등장 | 각 발생 위치를 구별하고 개정 후 첫 일치로 오복원하지 않음 |
| 이모지·조합 문자 앞뒤의 문장 | 원문 선택과 강조 경계가 깨지지 않음 |
| 일본어·한자와 한글 혼합 | 글자 누락·잘못된 영문 stemming이 없음 |
| 한국어 IME 조합 중 입력 | 중간 자모마다 무거운 질의를 확정하지 않음 |
| 범위 변경 직후 이전 query 응답 | 오래된 결과가 새 결과를 덮지 않음 |
| 읽지 않은 회차의 인물명 | 읽은 범위 검색의 자동완성·집계·snippet에 노출되지 않음 |

정확 구문 검색의 위치 정확도, 검색 상위 결과의 관련성, 누락률, 색인 크기, 초기 로드와 warm query 지연을 따로 측정한다. ‘한국어 지원’이라는 한 문구로 합격 처리하지 않는다.


# 11. 문학·텍스트 시각화: 실용 탐색과 감상 기능을 나눈다

## 11.1 시각화는 두 갈래가 모두 가능하다

**실용 탐색:** 특정 이름·장면·표현이 어디에 있었는지 찾는다. 결과를 누르면 정확한 원문으로 이동해야 한다.

**감상형 시각화:** 내가 읽은 작품의 패턴을 보기 좋게 남긴다. 작품 지문·독서 바코드·발췌 카드가 여기에 속한다. 바로 검색에 도움이 되지 않더라도 개인 서재의 소장감에 기여할 수 있다.

이전 보고서보다 감상형 기능을 적극적으로 인정한다. 단, 메인 Reader의 필수 로딩과 조작을 방해하지 않고, 분석 결과의 의미를 과장하지 않는 조건이다.

## 11.2 사용자가 제시한 도구 전체 재평가

도구의 기본 역할은 Voyant 공식 문서를 참고했다. 우선순위와 ReDSTM용 해석은 이 보고서의 제안이다. Voyant의 여러 명칭을 각각 독립적인 경량 npm 라이브러리처럼 취급하면 안 된다. [S5]

| 도구/개념 | 기본 역할 | ReDSTM에서의 해석 | 판단 |
|---|---|---|---|
| **Contexts / KWIC** | 검색어 앞뒤 문맥 | 기억하는 대사·설정의 회차별 문맥 검색 | **핵심 기능** |
| **MicroSearch** | 용어 분포를 압축 표시 | 검색 결과가 있는 회차/구간 미니맵 | **적극 추천** |
| **Trends** | 용어 빈도의 흐름 | 선택한 이름·장소·표현의 언급 추이 | 조건부 추천 |
| **Bubblelines** | 위치별 빈도 표현 | 이름 몇 개의 언급 위치를 병렬 비교 | 조건부 추천 |
| **Links** | 근접 용어 네트워크 | ‘같이 언급된 이름’ 탐색 | 별칭·문맥 검증 후 |
| **Knots** | 텍스트 패턴의 창작적 선 표현 | 개인 작품 지문·감상 카드 | 별도 실험 |
| **TextualArc** | 문서 순서와 용어 분포의 원호 표현 | 완독 후 작품 패턴 감상 | 별도 실험 |
| **StreamGraph** | 여러 용어 빈도 변화 | 선택한 용어군의 흐름 | 작은 비교에는 선 그래프가 더 나을 수 있음 |
| **WordTree** | 표현의 앞뒤 연결 | 반복 대사·호칭·문장 버릇 탐색 | 한국어 경계 검증 후 |
| **Mandala** | 용어와 문서의 관계 | 여러 작품과 태그·주제 연결 | 대형 개인 장서의 실험 기능 |
| **Correlations** | 빈도 변화의 동조 관계 | 이름·용어가 함께 증가하는 구간 탐색 | 분석용. 관계·인과로 부르지 않음 |
| **Text DNA** | 위치와 색으로 텍스트 시퀀스 비교 | 작품 지문·회차 바코드의 개념 레퍼런스 | 기존 전체 앱 이식보다 단순화 [S31] |
| **Novel Barcode** | 이 조사에서는 특정 단일 패키지를 확정하지 못함 | 읽기 상태/검색 위치/분량을 표현하는 바코드형 UI | 개념으로 자체 설계 |

TextDNA 원저자 설명은 GPU를 활용하는 자원 집약적 도구라는 점을 밝힌다. 오래된 연구 도구의 브라우저 호환 설명을 그대로 2026년 지원 상태로 옮기지 않는다. 여기서는 **시퀀스를 위치와 색으로 압축한다는 발상**을 차용한다. [S31]

## 11.3 가장 먼저 만들 시각화 조합

```text
용어 선택
   ↓
회차/구간 미니맵
   ↓
선택 구간의 KWIC 목록
   ↓
본문의 해당 문장
   ↓
원래 읽던 위치로 복귀
```

이 연결이 완성된 뒤 Trends·Bubblelines를 붙인다. 가장 비싼 관계도부터 만들고 원문 이동을 나중으로 미루지 않는다.

## 11.4 한국어 데이터 처리에서 주의할 점

‘학교’, ‘학교에’, ‘학교에서’를 어느 수준에서 합칠지, 인명·별칭·동음이의어를 어떻게 처리할지 먼저 정한다. 공백으로 나눈 영문 토큰 방식만 적용하면 한국어 빈도 해석이 달라질 수 있다.

분포를 계산할 때 **기준 분모**를 표시한다. 회차 길이가 다르면 원시 횟수와 길이당 빈도가 다르게 보인다. 시각화가 ‘얼마나 자주 언급됐나’를 보여주는지, ‘몇 회차에서 언급됐나’를 보여주는지 구별한다.

AA의 기호·공백과 footer·수집 안내·댓글을 산문 빈도 분석에 무조건 섞지 않는다. 댓글은 별도 corpus로 선택할 수 있게 한다. 인물의 이름 언급은 실제 등장이나 대사 횟수와 같지 않다.

## 11.5 스포일러는 그리기 전에 제한한다

미래 회차를 회색으로 가려도 자동완성·전체 결과 수·그래프 축·범례에 정보가 남으면 스포일러다.

```text
사용자가 허용한 읽기 범위
     ↓
대상 회차/블록 필터
     ↓
용어·별칭·snippet·빈도 집계
     ↓
차트와 결과 목록
```

단순히 `가장 큰 열람 회차 번호` 이하를 전부 읽은 것으로 보지 않는다. 건너뛰기·미리보기·다시 읽기가 있기 때문이다. **이 제품의 스포일러 제한은 독서 편의 기능**이며, 이미 내려받은 전체 원문에 대한 보안 접근제어와 동일하지 않다는 점도 구분한다.

읽은 범위가 좁아 그래프가 의미 없으면 그 사실을 표시한다. 전체 작품에서 계산한 상위 인물 목록을 필터링만 해서 숨기는 방식도 피한다.

## 11.6 시각화 구현 도구

| 후보 | 적합한 역할 | 판단 |
|---|---|---|
| 직접 SVG/Canvas | 단순 회차 지도·검색 위치·바코드 | 가장 작은 기능이면 직접 구현도 합리적 |
| **Observable Plot** | line·heatmap·small multiples 같은 통계 시각화 | **우선 비교 후보**. 라이브러리를 자체 호스팅해 사용할 수 있으며 Observable 클라우드 업로드를 전제하지 않음 [S29] |
| **D3** | 세밀한 상호작용·축·선택·커스텀 지도 | 자유도가 필요해질 때. 모든 차트를 처음부터 직접 만들 필요는 없음 [S62] |
| **Cytoscape.js** | 그래프·노드·관계 탐색 | 별칭·관계 데이터가 준비된 뒤 선택 [S30] |
| Voyant 전체 도입/서버 | 별도 분석 환경 | 관리 비용·한국어 처리·데이터 경계까지 감수할 때만 |

초기에는 **회차 지도 자체 구현 + Plot 비교**면 충분하다. 그래프 데이터가 없는데 Cytoscape만 추가해도 인물 관계도가 생기는 것은 아니다.

# 12. 라이브러리·플랫폼 기능 최종 검토표

## 12.1 읽는 방법

**우선 후보**는 기능을 만들 때 먼저 검증할 도구다. 지금 전부 설치하라는 뜻이 아니다. **조건부**는 특정 기능·프레임워크·데이터가 준비됐을 때 사용한다. **레퍼런스**는 시각·인터랙션 발상을 활용하되 직접 설치할 필요가 낮다는 의미다.

모든 패키지는 실제 채택 시 버전·라이선스·배포 파일·유료 기능 경계·보안 공지를 다시 고정한다. 공식 문서의 최신 표시가 stable이 아니라 beta일 수 있으므로 `latest` 문자열을 배포 설정으로 쓰지 않는다.

## 12.2 모션·장식·UI 컴포넌트

| 후보 | 활용할 수 있는 것 | 최종 판단·이유 | 근거 |
|---|---|---|---|
| **Motion** | 시트·도크·선택 상태·공유 요소 전환 | 조건부 우선. JS API 사용 가능. 필요한 모션이 단순하면 CSS로 시작 | [S32] |
| **AutoAnimate** | 작은 목록의 추가·삭제·재정렬 | Motion의 대안. 대형 가상 목록과 동일 DOM 영역에 무분별하게 중첩하지 않음 | [S33] |
| **Rough.js** | 서재의 작은 손그림 표식·작품 카드 장식 | 감상/개인화에 선택 도입. 앱 전체 손그림화는 별도 테마로 | [S34] |

## 12.7 조합의 권장안

**핵심 출시 경로의 최소안**

```text
현재 Reader core를 분리·보강
+ 테마 토큰과 새 작품/서재 UI
+ native dialog/popover를 우선 사용

+ 현재 회차 찾기에 Custom Highlight

+ 큰 목록에 검증된 virtualization 또는 페이지형 목록
```

**이후 필요할 때 추가**

```text
작품 검색 엔진 하나
+ 전체 정적 검색이 필요하면 Pagefind 비교
+ 통계 시각화가 필요하면 Plot
+ 한국어 파생 분석이 필요하면 Kiwi 배치
+ 이미지 확대가 부족하면 PhotoSwipe 비교
+ 정교한 전환이 필요하면 Motion 또는 AutoAnimate
```

두 검색 엔진·두 로컬 DB 래퍼·두 애니메이션 엔진을 같은 책임에 겹쳐 넣지 않는다. 패키지 수를 늘리는 것이 고도화의 지표가 아니다.

# 13. 구현 아키텍처

## 13.1 통합할 것과 분리할 것

**통합:** 검색 질의 형식, 작품/회차 표시 모델, Reader 행동, 읽기 설정, 문장 locator, 오류 표현, UI 컴포넌트.

**분리:** 소스별 원문 ID, 보존본 버전, 수집·배포 책임, 실제 원문, 사용자 메모, 재생성 가능한 색인, 비공개 접근 제어.

같은 작품으로 묶어 보여주는 것과 원본을 덮어쓰는 것은 다르다. 관계는 별도 레코드로 보관하고 오분류를 되돌릴 수 있어야 한다.

```text
Source adapters
  ├─ TypeMoon
  ├─ Novel text
  └─ Arcalive
         ↓
Display catalog / Work relationships
         ↓
ReaderDocument + ReaderSession
  ├─ Renderer: prose / AA / mixed / media
  ├─ Navigation: entry / sequence / return
  ├─ Locator: text ↔ DOM
  ├─ Find / annotation / footnote / TTS
  └─ Settings / reading profiles
         ↓
Optional exploration surface
  ├─ KWIC / chapter map
  ├─ term timeline
  └─ revision comparison
```

## 13.2 공통 locator 초안

아래는 **내부 모델 제안**이며 기존 스키마를 즉시 교체하라는 지시나 W3C 형식을 그대로 구현한 선언이 아니다.

```ts
type TextLocator = {
  schemaVersion: 1;
  source: "typemoon" | "novel" | "arcalive";
  documentId: string;       // source namespace 안의 안정적인 ID
  revision: string;         // 본문 hash 등 불변 버전 식별자
  blockId?: string;
  start: number;
  end: number;
  offsetUnit: "utf16";      // 브라우저 내부의 계약
  exact: string;
  prefix?: string;
  suffix?: string;
  viewportOffset?: number;
};

type Annotation = {
  id: string;
  locator: TextLocator;
  quote: string;            // 위치 복원 실패 시에도 보존
  note: string;
  style: string;
  createdAt: string;
  updatedAt: string;
  resolution: "exact" | "candidate" | "unresolved";
};
```

W3C Web Annotation의 quote와 앞뒤 문맥을 활용하는 발상은 참고할 수 있다. 외부 표준으로 내보낼 때는 그 표준의 문자 위치 규칙과 내부 UTF-16 단위를 명시적으로 변환한다. [S60]

### 복원 순서

1. 같은 revision의 검증된 block/offset을 우선한다.
2. 원문이 달라졌으면 exact quote의 모든 후보를 찾는다.
3. prefix/suffix·근접 block·원래 상대 위치로 후보를 검증한다.
4. 유일하게 검증되지 않으면 자동 확정하지 않는다.
5. 실패해도 원문 발췌와 사용자 메모를 삭제하지 않는다.

화면에 삽입한 이미지 오류 안내·도구 label·보조 번호는 원문 text model에 포함하지 않는다. 본문 렌더 변경 후 DOM mapping을 무효화·재생성하는 시점을 명시한다.

## 13.3 검색·분석 sidecar

파생 데이터는 실제 본문과 같은 release 계열로 묶는다.

```text
source document revision
  ├─ sanitized display representation
  ├─ search text + mapping
  ├─ optional term occurrences
  └─ metadata: producer version / corpus scope / checksum
```

서로 다른 release의 색인과 본문을 섞지 않는다. 새 색인이 없다고 이전 본문을 임의로 보여주거나, 검색 결과를 0으로 표시하지 않는다. 전체 색인 교체와 현재 읽는 회차는 독립적으로 실패 처리할 수 있어야 한다.

Kiwi나 차트 데이터 생성은 수집 원문을 덮어쓰지 않는 별도 작업이다. 캐시를 지우면 다시 만들 수 있어야 하고, 실패해도 마지막 정상 Reader가 계속 동작해야 한다.

## 13.4 프레임워크 결정: 현재 구조를 존중하되 신성시하지 않는다

| 경로 | 적합한 상황 | 장점 | 위험/비용 |
|---|---|---|---|
| ESM 모듈화 유지 | 현재 화면 수와 상호작용을 관리할 수 있음 | 가장 작은 이관, 현재 Reader 재사용 | 이벤트·상태·수동 DOM 코드가 계속 중복될 수 있음 |
| **ESM + Lit 등 점진 컴포넌트화** | 설정·검색·서재 등 재사용 UI가 늘어남 | 원문 Reader와 UI 주변부를 나눠 개선 | Shadow DOM·전역 스타일·selection 경계 설계 필요 |
| React 기반 UI 재구성 | 복합 상태와 여러 개발자가 다루는 UI 규모가 커짐 | Virtuoso·컴포넌트 생태계 활용 | 라우팅·초점·기록·DOM 소유권의 이관 비용 |
| Vue/Svelte 등 다른 프레임워크 | 팀이 해당 도구에 숙련되고 동일 검증을 통과함 | 선택지 확장 | 이름을 바꿔도 이관 검증은 사라지지 않음 |

**현재 추천은 Reader core를 먼저 분리하고, 새 서재/도구 패널에서 모듈화 또는 Lit의 작은 실험을 하는 경로다.** React를 금지하지 않는다. 반대로 Magic UI 한두 개를 쓰고 싶다는 이유만으로 전체 Reader를 옮기지는 않는다.

같은 본문 DOM을 기존 imperative code와 새 프레임워크가 동시에 관리하게 만들지 않는다. 읽기 본문은 하나의 소유자를 두고, shell·도구·상태 이벤트 경계를 명시한다.

## 13.5 빌드 도구도 재검토 가능하다

현재는 `index.html`이 `app.js`를 직접 읽는다. npm에 패키지를 추가했다고 브라우저 import가 자동으로 해결되지는 않는다. [R4][R5]

작은 번들러 또는 Vite 같은 빌드 경로를 도입하는 것은 금지가 아니다. 다만 기존 배포 산출물·CSP·Worker 경로·정적 asset versioning·source map 공개 범위를 확인한다. 목적은 라이브러리 설치 편의만이 아니라 **재현 가능한 빌드와 지연 로딩**이다.

패키지별 gzipped 광고 수치를 합산해 성능을 예측하지 않는다. 실제 산출물의 전송량, 파싱 시간, fonts, 색인, 이미지까지 측정한다.


# 14. 보안·프라이버시·저장 정책

## 14.1 원문을 제3자 서비스로 보내는 것은 별도 결정이다

비공개 보존 자료의 전문 검색·차트·문장 분석은 우선 자체 환경에서 처리한다. 브라우저 라이브러리를 사용한다는 사실과 외부 SaaS로 원문을 전송한다는 사실은 별개다.

Voyant 서버, LLM 요약, 원격 TTS, 표지 자동 생성, hosted search를 연결하는 경우 전송 대상·범위·보관 정책·비용·사용자 선택을 먼저 정한다. 이 보고서는 그러한 외부 전송을 승인하거나 실행하지 않았다.

## 14.2 원문 HTML과 새 UI의 신뢰 경계를 구분한다

원문은 표시할 콘텐츠이지 실행할 UI 코드가 아니다. 새 테마·정규식·Markdown·HTML 변환을 도입할 때 허용 tag/attribute/URL scheme/CSS 범위를 다시 검증한다.

`rehype-sanitize` 같은 도구를 추가해도 이후 플러그인이 위험한 HTML을 다시 만들면 전체 파이프라인은 안전하지 않을 수 있다. 정제 이후의 처리까지 검토한다. [S55]

사용자 지정 표지도 외부 임의 스크립트나 SVG 실행 경로로 이어지지 않게 한다. 로그·백업·검색어 분석에 원문 전문이나 인증 정보가 불필요하게 들어가지 않도록 한다.

## 14.3 사용자 데이터와 캐시를 분리한다

| 데이터 | 성격 | 보관 정책 |
|---|---|---|
| 원본 보존본 | 서버의 canonical archive | 현재 보존 정책을 유지 |
| 검색 색인·통계 | 재생성 가능 | 버전별 삭제·LRU 가능 |
| 오프라인 본문 | 다시 받을 수 있지만 민감할 수 있음 | 사용자가 범위·용량·삭제를 제어 |
| 표시한 문장·내 메모 | 대체 불가능한 사용자 기록 | 자동 캐시 정리 대상에서 제외 |
| 읽기 위치·프로필 | 사용자 경험 상태 | schema migration·백업·복원 |
| 사용자 표지·별칭 | 개인화 기록 | 원문과 분리·내보내기 가능 |

IndexedDB로 옮긴다고 영구 보존이 보장되지는 않는다. 브라우저 저장소에는 quota와 eviction 정책이 있으므로 저장 실패·사용자 삭제·기기 변경·백업을 설계해야 한다. `persist()` 요청 역시 성공을 무조건 보장하지 않는다. [S59]

localStorage에서 IndexedDB로 이전한다면 읽기→쓰기→검증→활성화 순서를 두고, 성공 검증 전 기존 데이터를 지우지 않는다. 백업 형식의 과거 호환을 유지하고, 새 데이터가 있는 상태에서 구버전 UI로 롤백했을 때의 동작도 정의한다.

## 14.4 인증과 오프라인은 동시에 완벽할 수 없다는 점을 명확히 한다

이미 기기에 내려받은 평문을 서버에서 즉시 회수할 수는 없다. 따라서 다음 중 어떤 정책인지 제품에 명시해야 한다.

| 정책 | 장점 | 대가 |
|---|---|---|
| 캐시 본문도 온라인 인증 이후에만 표시 | 인증 만료 동작이 단순 | 완전한 오프라인 읽기가 아님 |
| 사용자가 지정한 작품은 오프라인 허용 | 이동 중 읽기 가능 | 서버의 즉시 접근 취소와 기기 저장본의 접근이 일치하지 않음 |
| 기기 잠금/암호화 계층 추가 | 기기 내 노출을 줄일 수 있음 | 키 관리·복구·사용성·위협 모델을 별도 설계해야 함 |

권장은 처음부터 모든 작품을 오프라인화하지 않고, **이 기기에서 저장한 자료의 범위와 로그아웃 시 처리 정책을 명시하는 선택 기능**으로 시작하는 것이다. 브라우저 인증 캐시를 우회하는 Service Worker가 생기지 않는지 실제 테스트한다.

## 14.5 접근성은 기존 규정을 버려도 유지해야 하는 설계 목표다

키보드 초점, 스크린리더 label, 터치 영역, 대비, 확대, reduced motion을 완성 조건에 포함한다. 반투명·종이색·작품색은 이 조건을 통과하면 사용할 수 있다.

모달이 아닌 popover에 불필요한 focus trap을 걸거나, 모달을 열었는데 배경의 이전/다음 버튼이 그대로 동작하게 하지 않는다. 큰 가상 목록은 현재 선택된 행과 키보드 초점을 재활용 DOM 때문에 잃지 않아야 한다.

# 15. 성능과 품질 검증 계획

## 15.1 먼저 측정할 데이터

현재 장서의 작품 수·회차 수·제목 길이·본문 크기·AA 최대 폭·이미지 수·댓글 수를 분포로 집계한다. 단일 평균만으로 검증 자료를 만들지 않는다.

본문에는 소형·중간·대형과 극단적인 outlier를 포함한다. 실제 민감한 원문을 외부 벤치마크 서비스로 올리지 않고, 자체 기기에서 평가하거나 구조가 같은 합성 fixture를 쓴다.

## 15.2 제안하는 초기 품질 목표

다음 수치는 **현행 측정 결과나 보장 성능이 아니라 구현팀이 검증할 초기 목표**다. 실제 코퍼스와 기기 측정 후 조정한다.

| 영역 | 초기 목표 | 방법 |
|---|---|---|
| 목록 | 회차 수가 커져도 DOM이 비례해 무한 증가하지 않음 | 가상화면 overscan 포함 row 수 상한을 관찰. 페이지형 대안도 비교 |
| warm 검색 | 입력 종료 후 결과 갱신 p95 200ms 이내를 목표 | 색인 warm/cold·기기·query 종류를 분리 측정 |
| 읽기 위치 | 테마·서체·화면 회전 후 같은 원문 문장이 유지됨 | 단순 pixel 오차뿐 아니라 locator 일치 검증 |
| 회차 직접 이동 | 대상 이전 모든 행 생성에 의존하지 않음 | 아주 먼 회차의 DOM 생성량·응답 측정 |
| 검색 취소 | 오래된 응답이 최신 결과를 덮지 않음 | 빠른 입력·작품/필터/범위 변경 테스트 |
| 주석 | 위치 복원 실패에도 quote와 메모가 남음 | 원문 개정·삭제·중복 문장·백업/복원 |
| 스포일러 | 설정 범위 밖 정보가 자동완성·집계에 나오지 않음 | 범례·count·alias·snippet까지 검사 |
| 모션 | 효과 비활성화와 reduced motion에서도 모든 기능 완전 | animation 없이 E2E 실행 |
| 저장 | quota/transaction 실패 시 성공으로 표시하지 않음 | 오류 주입·다중 탭·기기 저장소 삭제 |
| 앱 시작 | 읽기에 불필요한 분석·차트·TTS·추가 서체 미로드 | 네트워크 waterfall·실제 bundle 확인 |

‘100점 Lighthouse’ 같은 단일 점수로 완성도를 대체하지 않는다. 긴 회차를 읽다 폰트를 바꾸고 Back으로 돌아오는 실제 시나리오가 통과해야 한다.

## 15.3 필수 fixture

1. **긴 한국어 소설:** 대사, 여러 문단, 반복 문장, 긴 제목.
2. **AA 중심 글:** 전각·반각·특수문자·색·극단적으로 긴 한 줄.
3. **혼합 글:** 산문 사이 AA, 이미지, 원문 주석.
4. **지연 이미지 글:** 일부 정상·일부 만료·일부 미보존.
5. **대형 목차:** 외전·프롤로그·누락·번호 중복/소수점.
6. **개정본:** 앞부분 삽입·삭제, 동일 문장 여러 위치, 단락 순서 변경.
7. **한국어 검색:** 초성·공백·1~2글자·한자·반복 기호·IME.
8. **사용자 기록:** 많은 메모, 저장 실패, 백업 병합, 구버전 복원.

## 15.4 실제 동선 검증

| 시나리오 | 합격 조건 |
|---|---|
| 목록의 중간 회차 열기→다섯 회차 이동→Back | 원래 목록 맥락·필터·위치로 돌아옴 |
| 글 중간에서 서체와 크기 변경 | 같은 문장 근처가 유지되고 보정이 반복 진동하지 않음 |
| AA 확대→가로 이동→다음 회차→복귀 | 저장 정책에 맞게 배율·가로 위치 복원 |
| 검색 결과로 미래 회차 잠깐 미리보기→닫기 | 이어읽기 진도를 몰래 덮지 않음 |
| 검색어 입력 중 작품 전환 | 이전 작품의 결과·하이라이트가 새 본문에 남지 않음 |
| 문장 선택→스크롤→메모 | 선택 핸들과 메뉴 충돌 없이 올바른 quote 저장 |
| Android 키보드가 열린 검색/설정 | 닫기·결과·활성 입력이 가려지지 않음 |
| 인증 만료·오프라인·보존 누락 | 서로 다른 상태와 복구 행동 |
| 작품 표지/테마 변경 | 본문 설정·AA 원문색·사용자 기록이 유지됨 |
| 외전 포함 목차 정렬 변경 | 이전/다음의 읽기 순서가 목록 정렬에 오염되지 않음 |

## 15.5 시각 QA를 위한 비교 화면

기존 중립안, 편집형 청록안, 작품색 강조안을 **동일한 데이터**로 비교한다. 새 안에만 예쁜 표지·짧은 제목을 넣고 기존 안에는 긴 오류 자료를 넣는 비교는 무효다.

모바일·데스크톱·다크·글자 크게·긴 제목·원본색 AA·이미지 실패 상태를 모두 포함한다. 데스크톱 브라우저의 모바일 에뮬레이션은 실제 Samsung Internet/Chrome Android의 키보드·뒤로가기·선택 동작 검증을 대체하지 않는다.

# 16. 단계별 구현 계획과 인계 작업

## 16.1 우선순위 원칙

라이브러리 설치 순서가 아니라 **완결된 사용자 경험 단위**로 작업한다. 아래 순서는 병렬 작업을 금지하는 일정표가 아니라 의존성과 검증 순서다. 기간 추정은 포함하지 않는다.

| 단계 | 목표 | 산출물 | 통과 조건 |
|---|---|---|---|
| **P0** | 근거와 기준 확보 | 실제 데이터 분포, golden fixtures, 3개 테마 비교, 현행 동선 기록 | 무엇을 개선하는지 측정할 수 있음 |
| **P1-A** | 서재의 외형·구조 개선 | 작품 중심 정보 모델, 컴팩트/카드, 이어읽기, 새 토큰 | 원래 탐색과 저장 기록이 퇴행하지 않음 |
| **P1-B** | 읽기 핵심 개선 | locator 보강, 현재 회차 찾기, 도구층·모바일 동선 | Back·폰트 변경·AA·검색 취소 통과 |
| **P1-C** | 긴 목록 개선 | 페이지형/가상화 비교 및 채택 | 먼 회차 접근과 초점/복원 통과 |
| **P2-A** | 저장과 재발견 | 문장 메모·발췌함·스마트 서재 | 백업·개정·오류 주입 통과 |
| **P2-B** | 작품 검색 | 한국어 벤치마크, 엔진 하나 선정, KWIC·회차 지도 | 검색 의미·짧은 query·스포일러 검증 |
| **P3** | 선택 확장 | 오프라인, TTS, 용어 추이, 버전 비교, 인쇄/EPUB | 기능별 실제 수요와 비용을 확인 |

오프라인 읽기 수요가 강하면 P3의 오프라인을 분석 그래프보다 먼저 구현한다. 실측에서 목록 문제가 없다면 가상화 전환보다 다른 과업을 앞당길 수도 있다. 로드맵을 새로운 절대 규정으로 만들지 않는다.

## 16.2 작업 티켓 초안

| ID | 작업 | 주요 변경 경계 | 완료 조건 |
|---|---|---|---|
| UX-01 | 기존 디자인 규칙 분류·새 원칙 반영 | DESIGN.md와 관련 문서 | 미적 금지와 안전 계약이 분리됨 |
| UX-02 | 테마 토큰·밀도·읽기 프로필 분리 | app.css·설정 UI | 앱 테마가 본문/AA 설정을 덮지 않음 |
| UX-03 | 작품 카드·작은 타이포 표지 | 서재/작품 UI | 원본표지/사용자표지/대체카드 구별 |
| UX-04 | 출처 중심/작품 중심 탐색 공존 | index/app/text-library 접점 | 소스 필터를 잃지 않고 공통 탐색 가능 |
| READ-01 | text model/DOM locator 모듈 | text-anchor 및 본문 렌더 접점 | 반복 문장·revision·UI 삽입 fixture 통과 |
| READ-02 | 현재 회차 찾기 | 공통 Reader 도구 | 양쪽 Reader 경로에서 같은 동작 |
| READ-03 | 모바일 도구·각주 복귀 | navigation/tool state | Back·IME·선택·safe-area 검증 |
| LIST-01 | 대형 목차 제한 렌더링 | text-library/list-anchor | 직접 회차 이동 시 앞부분 전체 생성 불필요 |
| DATA-01 | 주석 저장·백업 확장 | local user-state repository | 캐시 정리와 사용자 기록의 분리 |
| SEARCH-01 | 한국어 golden query 구축 | 테스트·fixture | 기대 정확 결과와 허용 유사 결과 명시 |
| SEARCH-02 | 후보 엔진 비교 | 독립 실험 코드 | 정확도·원문 위치·메모리·전송량 기록 |
| SEARCH-03 | 작품 KWIC와 지도 | source sidecar/worker/UI | 새 본문과 옛 색인이 섞이지 않음 |
| MEDIA-01 | 이미지 확대 비교 | 기존 media 모듈 경계 | 만료·긴 이미지·뒤로가기·lazy load 통과 |
| EXPLORE-01 | 용어 추이·작품 지문 | 선택적 탐색 패널 | raw count/분모/범위/원문 연결 표시 |

파일명은 현재 확인한 모듈을 기준으로 한 시작 지점이다. 구현 전에 실제 import와 책임 경계를 따라 최종 범위를 확정한다. 큰 `app.js`를 한 번에 모두 다시 작성하는 작업과 새 기능 출시를 묶지 않는다.

## 16.3 기능 플래그와 롤백

새 테마, 새 목록 렌더러, 새 검색, 문장 주석을 각각 독립적으로 켜고 끌 수 있게 한다. 플래그를 끄면 **기능 UI만** 돌아가야 하며 이미 작성한 메모를 지우면 안 된다.

장서 release와 UI build의 호환 범위를 명시한다. 지원하지 않는 새 필드가 들어오면 무시 가능한지, 명시적 오류여야 하는지 정한다. 새 검색 실패가 기존 Reader를 가로막지 않게 한다.

## 16.4 지금 하지 않을 일

새 의존성을 일괄 설치하지 않는다. 보존 자료를 전체 변환하거나, 모든 회차를 자동 분석하거나, 전체 앱을 React로 이관하거나, 모든 원문을 Markdown/EPUB로 바꾸는 작업을 첫 단계로 삼지 않는다.

대신 다음 한 흐름을 먼저 완성한다.

> **서재에서 작품을 식별 → 이어읽기 → 현재 회차에서 문장 찾기 → 원래 위치 복귀 → 목록으로 한 번에 돌아오기.**

이 흐름 위에 문장 기록과 작품 검색을 추가하면 시각 개선과 기능 개선의 효과를 따로 확인할 수 있다.

ReDSTM은 비공개 보존 자료를 작품 중심으로 찾고,

# 18. 최종 결정 요약

## 18.1 디자인

**추천:** 편집형 서재를 기본으로, 작품별 작은 표지·타이포그래피·고정된 색을 결합한다. 카드형과 컴팩트형을 모두 제공하고, 본문 읽기 프로필과 AA 프로필은 독립시킨다.

**재허용:** warm neutral, 명조 제목, 보라/청록 등 새로운 강조색, 부분적인 반투명 도구, 작은 그림자·정적 그라데이션, 사용자 이모지 서재, Rough Notation 기반 개인 기록.

**계속 제한:** 실제 읽는 글을 가리는 연출, 정보 없는 대형 장식, 움직이는 본문 배경, 자동 스포일러 노출, 원문 파괴, 선택·스크롤을 가로채는 전면 제스처. 이것은 취향 금지가 아니라 목적과 비용에 따른 판단이다.

## 18.2 기능

**가장 먼저:** 작품 중심 탐색·이어읽기 개선, 한국어 현재 회차 찾기, locator 보강, 큰 목차의 직접 이동.

**그다음:** 발췌·메모, 스마트 서재, 작품 검색/KWIC, 회차 지도.

**선택적으로:** 각주/댓글 왕복, 별칭 사전, 일반 이미지 gallery, 오프라인 읽기, TTS, 변경본 비교, 용어 추이, 작품 지문, EPUB/인쇄.

## 18.3 기술

**현재와 자연스럽게 결합:** CSS Custom Highlight, Floating UI DOM, es-hangul, TanStack Virtual core, idb 또는 Dexie.

**이번에 비교 범위를 넓힌 핵심 후보:** Pagefind, FlexSearch, Kiwi, Lit, Web Awesome Core, Observable Plot, PhotoSwipe, foliate-js, native Popover/View Transitions.

**설치보다 목적을 먼저 볼 것:** Animate UI·Magic UI·Aceternity UI·Rough.js·Lenis·React Virtuoso·Vivliostyle.

**목적이 다른 것:** string-width·xterm.js·ansi_up을 AA Reader의 기본 엔진으로 사용하는 접근.

## 18.4 아직 확정하지 않는 것

실제 최종 색상·기본 본문 서체·검색 엔진 승자·React 전환 여부·가상화 임계 규모·TTS 백그라운드 범위는 실측 없이 확정하지 않는다.

Orama의 한국어는 공식 README에서 experimental로 확인했지만 실제 선택할 릴리즈의 패키지와 품질은 추가 검증 대상이다. Novel Barcode는 이번 조사에서 단일 공식 라이브러리로 특정하지 못했으므로 개념으로 다뤘다.

기술 문서의 최신 기능 표시는 제품에 바로 설치 가능한 stable 상태와 다를 수 있다. 이 문서는 **도입 판단과 검증 기준을 확정한 보고서**이지, 미실행 코드를 검증 완료로 선언한 인증서가 아니다.

**한 문장으로 정리하면, ReDSTM은 기존의 미적 규칙을 지키는 프로젝트가 아니라 원문과 읽기 경험을 지키면서 더 매력적인 개인 서재로 발전시킬 수 있는 프로젝트다.**

## 19.3 출처 해석상의 주의

한국어 조판 문서는 확인본의 초안 성격을 고려한다. 고전 Mona Font와 Text DNA는 현재 모바일 브라우저용 최신 제품으로 추천한 것이 아니라 호환성·표현 방식의 근거로 사용했다. Orama 한국어 tokenizer의 experimental 표시는 실제 배포할 패키지 버전과 함께 다시 확인해야 한다.

**Novel Barcode는 단일 공식 패키지·원저자 구현으로 특정하지 못했다.** 따라서 특정 제품의 유지보수·라이선스·성능을 단정하지 않고, 바코드형 텍스트 시각화라는 개념으로만 다뤘다.

이 보고서의 컬러 대비 수치는 제안 색 조합에 대한 계산이며, 실제 전체 화면의 접근성 검사를 대체하지 않는다. 검색 지연·폰트 선호·모바일 제스처·가상화 임계값은 검증 계획이지 측정 결과가 아니다.
