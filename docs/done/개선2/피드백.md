**작품 모아보기는 단일 엔진으로 통합하는 것이 맞습니다. 다만, 제목 파서 두 개를 합치는 정도로는 별도 운영이 없어지지 않습니다.** 작품 소속을 결정하는 단계부터 회차 정렬, 중복 보존본 처리, 작품 ID, 기존 읽기 기록의 이행까지 공통화해야 합니다.

## 2. 가장 먼저 고쳐야 할 발견: 작품 제목이 회차 제목으로 바뀝니다

### `parse_work_detail()`의 변수 재사용 버그

텍스트 수집기의 `scripts/text_archive/collector.py`에서 작품 제목을 `title`에 넣은 뒤, 회차를 순회하면서 **같은 `title` 변수를 회차 제목으로 덮어씁니다.** 마지막에는 그 변수를 작품 제목 자리에 반환합니다.  

합성 입력으로 재현한 결과는 다음과 같습니다.

```text
입력 작품명: 실제 작품 제목
회차 목록: 1화 출발 / 2화 재회

반환된 작품명: 2화 재회

회차 배열을 역순으로 넣으면:
반환된 작품명: 1화 출발
```

이 문제는 단순히 화면 제목이 이상해지는 데 그치지 않습니다. `_apply_work()`는 반환된 제목을 작품명과 매칭용 `title_key`에 저장하고, `_apply_episode()`는 그 작품명을 회차 자료에 가져옵니다. **잘못된 입력으로 작품 매칭을 수행할 수 있는 경로**입니다.  

따라서 순서는 다음이어야 합니다.

**제목 변수 분리 → 기존 메타데이터 영향 조사 → 검증된 원본 작품명으로 복구 → 후보 키 재계산 → 새 매칭 알고리즘 적용.**

실제 운영 데이터에서 몇 작품이 영향을 받았는지는 아직 확인하지 못했습니다. 또한 수집기만 수정한다고 이미 저장된 잘못된 제목이 모두 복구되지는 않으므로, 명세서에서는 **원본 작품 메타데이터와 기존 item의 표시 메타데이터를 함께 점검하도록** 했습니다.

### 이미 얻은 회차 번호도 후단에서 잃고 있습니다

같은 파서는 원본 응답의 `episodeNumber` 또는 `number`를 읽습니다. 그런데 이후 `_apply_work()`의 DB 저장에는 이 값이 유지되지 않습니다. **원본에서 정확한 회차 번호를 얻고도, 나중에 제목을 다시 해석하게 만드는 구조**입니다.  

알고리즘 고도화에서 가장 먼저 할 일은 더 영리한 추측이 아니라, **이미 알고 있는 정보를 버리지 않는 것**입니다.

## 3. 현재 제목 분석기의 한계도 구체적으로 확인했습니다

현재 파서는 보수적인 후보 생성기로서 장점이 있지만, 그대로 전체 작품의 기준으로 삼기에는 제약이 큽니다. Python과 JavaScript에 유사한 구현이 중복되어 있기도 합니다.  

| 확인한 동작 | 문제가 되는 상황 | 개선 방향 |
|---|---|---|
| 회차 중복 한 건이 있으면 후보 그룹 전체 제외 | `1화, 2화, 3화, 2화`에서 작품 전체가 후보에서 사라짐 | 중복된 회차만 충돌 처리 |
| 제목 끝의 명시적 회차 중심 | `12화 (완)`, `제12화: 귀환`, `Chapter 12` 등을 놓침 | 단계식 파서로 접미 태그·부제·회차를 분리 |
| 짧은 작품명 일률 제외 | 실제 두 글자 작품명도 누락 | 짧은 제목에는 더 강한 보조 근거를 요구 |
| 괄호·범위 검증 부족 | `(1]`, `3~1화`도 파싱 | 문법 오류와 모호한 입력을 구분 |
| 합본 구간 중복 미검출 | `1~3화`와 `2화` 공존 | 회차 범위와 원본 파일을 별도 모델링 |
| 막간·권별 프롤로그 표현 부족 | 막간이 항상 앞에 오거나 권별 프롤로그가 다른 작품으로 분리 | 원본 목차 순서와 상대 위치를 보존 |
| Python·JS 정규화 차이 | 같은 제목 집합이 언어별로 다르게 처리될 수 있음 | 서버 단일 파서로 확정 |

여기서 **“보수적이니 전부 느슨하게 바꾸자”는 해결책은 좋지 않습니다.**

예를 들어 작성자 조건과 게시판 조건을 제거하면 게시판 이동이나 번역자 변경은 잘 연결될 수 있지만, 동명 작품과 다른 번역까지 잘못 합칠 가능성이 커집니다. 필요한 것은 조건의 일괄 완화가 아니라 **제목 외의 근거를 활용하는 별도 연결 경로**입니다.

## 4. 추천 구조: 하나의 Python 작품 엔진 + 출처별 어댑터

제가 권하는 구조는 다음과 같습니다.

```text
타입문넷 자료 ── TypeMoon 어댑터 ─┐
텍스트 소설 ─── Novel 어댑터 ─────┼─ 공통 작품 엔진
아카 자료 ───── Arca 어댑터 ──────┘
                                  │
                    소속·동일 작품·회차·순서·중복 판정
                                  │
                    안정 ID / 근거 / 수동 보정 기록
                                  │
                    공통 summary / detail / membership
                                  │
                     타입문넷·텍스트 장서 공통 소비
```

**브라우저는 작품을 다시 묶지 않습니다.** 서버가 게시한 작품 소속과 회차 순서를 읽고 표시합니다.

공통 엔진에는 제목 정규화, 후보 검색, 소속 판정, 출처 간 작품 연결, 회차 대응, 순서, 중복 보존본, ID·별칭, 수동 보정과 이행을 넣습니다. 출처별 어댑터에는 원본 HTML·JSON·Markdown 해석과 원본 ID·번호·목차 추출만 남깁니다.

**기존 DB를 당장 하나로 합칠 필요는 없습니다.** 기존 원문 저장소와 수집 경로를 유지하면서, 공통 엔진이 필요한 메타데이터와 작품 관계를 별도 레지스트리로 관리하는 편이 안전합니다.

### 중요한 구분: 작품·독서 순서·회차·원본 파일

이 네 가지는 분리하는 것이 좋습니다.

| 개념 | 예시 |
|---|---|
| **작품** | 독자가 인식하는 하나의 소설 |
| **독서 순서/판본** | 원래 연재판, 리메이크판, 번역자 A판 |
| **논리 회차** | 본편 12화, 12화 하편, 막간 |
| **원본 자료** | 타입문넷 게시글, 다른 출처의 같은 회차 파일 |

이렇게 해야 **같은 작품으로 모아 보여주면서도, 다음 화에서 다른 번역이나 리메이크로 갑자기 넘어가는 문제를 막을 수 있습니다.**

“같은 작품”, “같은 회차”, “같은 본문 파일”을 한 판정으로 처리하면 안 됩니다.

## 5. 제목 외에 활용할 정보는 충분히 있습니다

우선순위를 다음처럼 잡는 것이 좋습니다.

| 정보 | 활용 |
|---|---|
| **원본 작품 ID·부모 관계** | 같은 출처 내 작품 묶기의 최우선 기준 |
| **원본 목차 순번·회차 번호** | 제목 추측보다 신뢰할 수 있는 회차 순서 |
| **작성자·게시자·번역자** | 동명 작품 구별과 후보 축소. 역할은 분리 |
| **원작 URL·작가가 만든 목차 링크** | 제목 변경·게시판 이동·번역 관계 복원 |
| **작성 시각** | 순서가 모호할 때의 보조 근거 |
| **본문 해시와 반복 빈도** | 다른 출처의 동일 본문 후보 확인 |
| **기존 작품 소속·수동 보정** | 누적 데이터의 연결과 사용자 의도 보존 |
| **판본·리메이크·언어·분류 정보** | 잘못 합치면 안 되는 경계 확인 |

타입문넷 수집 자료에는 이미 작성자·분류·시각·원문 URL·HTML·텍스트·AA 여부 등이 있습니다. 텍스트 소설에는 출처별 작품·회차 ID와 본문 해시가 있습니다. 먼저 이 정보들이 **수집 → 저장 → 작품 엔진 → 게시** 전체 과정에서 유지되는지 점검해야 합니다.   

아카라이브는 보존 Markdown의 알려진 헤더 형식에 작성자·시각·URL이 들어 있는 사례가 테스트에 있습니다. 실제 파일의 형식과 보존율을 조사하면, **전부 재수집하지 않고도 기존 자료에서 메타데이터를 보강할 여지**가 있습니다. 다만 모든 실제 파일이 그 형식이라는 뜻은 아닙니다. 

또한 **작성자 미상끼리 같다고 해서 같은 작성자가 아닙니다.** 빈 값이나 `작가 미상`은 일치 근거가 아니라 정보가 없다는 뜻으로 처리해야 합니다.

## 6. 알고리즘은 ‘전수 클러스터링’보다 단계적으로 판단하는 구조가 적합합니다

추천 파이프라인은 다음과 같습니다.

**원본 부모 관계 적용 → 제목·회차 구조 파싱 → 좁은 후보 검색 → 여러 근거와 모순 검사 → 자동 확정/검토/보류 → 회차 순서 확정 → 게시**

### 후보는 넓게 찾되, 확정은 보수적으로

후보를 찾는 통로를 여러 개 둡니다. 정확한 제목·작성자 조합, 등록된 제목 별칭, 원작 링크, 본문 해시, 제한된 범위의 퍼지 제목 검색 등이 각각 후보를 회수합니다.

하지만 후보가 생겼다고 바로 병합하지 않습니다. 리메이크 표시, 다른 번역, 동일 회차의 본문 충돌, 기존 “다른 작품” 판정 등을 검사합니다.

**A와 B가 비슷하고 B와 C가 비슷하다고 A·B·C를 전부 합치지 않는 것**도 중요합니다. 기존 큰 작품 두 개를 합치는 작업은 신규 회차 한 건을 편입하는 작업보다 훨씬 강한 검증을 요구하도록 설계했습니다.

### 기존 본문 해시 로직은 유지하되 보완해야 합니다

현재 소설 연결 로직은 제목·저자 외에도 공통 회차 signature와 본문 해시를 요구합니다. 이 방향은 유지할 가치가 있습니다. 

다만 재현 결과, **공통 signature 두 개가 서로 다른 본문 두 개를 의미하지는 않았습니다.** 같은 안내문 해시가 1화와 2화 라벨에 반복되면 signature는 두 개가 될 수 있습니다.

따라서 “여러 회차에서 일치”는 다음을 함께 확인해야 합니다.

**서로 다른 고유 본편 해시인가, 공통 안내문이 아닌가, 회차 대응과 순서가 모순되지 않는가.**

반대로 같은 뜻의 `제1화`, `1화`, `01화`가 현재는 다른 키라서 놓치는 문제도 있습니다. 회차 의미와 원래 라벨을 분리하면 이 부분을 개선할 수 있습니다.

## 7. 라이브러리는 이렇게 선택하는 것이 좋겠습니다

**현재 우선 조합은 Python 표준 라이브러리 + SQLite + 선택적 RapidFuzz + 테스트용 Hypothesis입니다.** 새로운 벡터 DB나 대형 프레임워크가 먼저 필요하지는 않습니다.

| 도구 | 판단 | 적용 범위 |
|---|---|---|
| **RapidFuzz** | 제한적으로 추천 | 이미 좁힌 후보 안에서 제목 유사도 계산 |
| **SQLite FTS5** | 필요할 때 | 부분 제목 검색·후보 회수 |
| **Hypothesis** | 개발용 추천 | 병합·분리·재수집·되돌리기의 상태 기반 테스트 |
| **문자 n-gram TF-IDF** | 비교 실험 후보 | 띄어쓰기·제목 변화에 대한 후보 회수 개선 |
| **MinHash/LSH** | 후순위 | 본문 near-duplicate 후보 검색 |
| **Splink** | 현재 첫 선택은 아님 | 메타데이터가 풍부해진 뒤 확률적 동일 작품 연결 비교 |
| **임베딩·LLM** | 검토 보조 | 애매한 후보 제안. 자동 병합·삭제의 최종 권한은 부여하지 않음 |

RapidFuzz의 `token_set_ratio`는 한 문자열의 단어 집합이 다른 쪽에 포함되면 100이 될 수 있습니다. 따라서 높은 점수를 **같은 작품·같은 판본이라는 확률**로 해석해서는 안 됩니다. :chatgpt-content-reference{index="19"}

FTS5 trigram은 후보 검색에 유용하지만 3문자 미만의 full-text query 제한을 고려해야 합니다. 두 글자 한국어 작품명에는 별도 exact 검색이나 제한된 fallback이 필요합니다. :chatgpt-content-reference{index="20"}

Splink는 복수 필드의 레코드 연결에 적합한 도구이고, 공식 문서도 단일 bag-of-words 열만 연결하는 용도로 설계되지 않았다고 설명합니다. 현재는 먼저 **손상된 제목, 버려지는 번호, 중복된 판단 경로, 불완전한 ID 이행**을 해결하는 편이 낫습니다. :chatgpt-content-reference{index="21"}

## 8. 쌓인 데이터 때문에 ‘전면 재생성’은 피해야 합니다

저장소의 과거 검토 문서에는 다음 결과가 있습니다.

**당시 로컬 보존본에서 기존 작품 소속 글 168,102건 중, 새 exact preview 후보에 포함되지 않은 글이 131,341건**이었습니다. 이 수치는 2026-07-11 로컬 보존본을 대상으로 한 과거 조사이며, 이번 운영 DB 실측이나 정확도 지표는 아닙니다. 하지만 기존 목록을 새 파서 결과로 통째로 대체하면 위험하다는 점은 잘 보여줍니다. 

그래서 이행은 다음 원칙으로 잡았습니다.

**기존 작품을 보존한 상태로 새 엔진을 병렬 평가하고, 확실한 신규 회차 편입부터 적용합니다.** 새 파서가 해석하지 못했다는 이유로 기존 소속을 지우지 않습니다. 기존 작품의 병합·분리는 별도 변경 계획과 되돌리기 정보를 요구합니다.

### 작품 ID만 보존해서는 부족합니다

PC importer와 Oracle 수집 경로는 canonical chapter ID에 서로 다른 접두 형식을 사용할 수 있습니다. 또한 브라우저의 현재 migration은 작품 ID 접두를 옮기는 처리가 중심입니다. 대표 회차 파일이 바뀌는 경우까지 보존하려면 **작품 별칭뿐 아니라 회차·원본 자료 별칭**도 필요합니다.   

그리고 과거의 약한 자동 병합을 복구하는 migration에는 **출처가 정확히 두 개인 그룹만 실제로 분리하는 조건**이 있습니다. 세 개 이상인 그룹은 별도로 점검해야 합니다. 새 매칭 알고리즘을 고쳤다고 기존 오병합이 저절로 풀리는 것은 아닙니다.
