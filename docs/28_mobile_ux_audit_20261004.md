# 모바일 화면·흐름 UX 점검 (2026-10-04)

성격: `docs/26_ux_laws_research.md`의 평가 질문(§2.4)·시작표(§6.6)를 실제 앱에 적용한 **점검 기록**.
확정 설계는 `DESIGN.md`·`docs/24_frontend_redesign_spec.md`가 우선하며, 아래 개선안은 제안이다.

## 0. 점검 방법과 범위

- 환경: 로컬 `wrangler dev` + E2E fixture(타입문넷 40편 연재, 소설 2작품, 아카라이브 2글), Playwright Chrome,
  **384×800**(`DESIGN.md` §4.1 S22+ 기준), 터치 에뮬레이션(Pixel 7 프로필). main `4fe4435` 기준.
- 방식: 정답 위치를 미리 정하지 않고 실제로 읽고·저장하고·찾으며 화면을 이동. 각 단계 화면을 캡처해 판정.
  같은 문제를 두 번째 실행에서 다시 확인했고, 재현되지 않은 것은 §4에 따로 적었다.
- 판정 표기(`docs/26` §6.6): **재현** · **코드 확인** · **미검증(이유)**.
- 우선순위(`docs/26` §6.4): 기록 손실·오도 → 핵심 과제 차단 → 반복 마찰 → 시각 인상.

## 2. 항목별 상세

### 1. 선택 메뉴 고정 바가 줄어 글자가 쪼개짐 — 높음

- **관찰**: 본문 문장을 선택하면 도크 자리에 짙은 바가 뜨는데, 폭이 약 230px로 줄어 `표 / 시`, `메 / 모`, `복 / 사`처럼
  세로로 깨진다. 바가 도크 왼쪽(목록·이전·다음)만 덮어 `설정·더보기`가 옆에 그대로 보인다.
- **원인(코드)**: `styles/reader.css:80` `.selection-menu.fixed { left: 12px; right: 12px; … }`. popover의 UA 기본
  `width: fit-content`가 남아 left/right로 늘어나지 않는다.
- **근거**: `DESIGN.md` §7.8(고정 바는 같은 4개를 보이는 정식 대체 배치), §7.11 도크 자리 점유, Nielsen #4, 피츠.
  OS 선택 핸들과 겹치는 실제 휴대폰에서 이 배치가 쓰이므로 발췌·메모 과제(G7)의 첫 단계가 깨진다.
- **개선안**: `.selection-menu.fixed`에 `width: auto`(또는 `inline-size: auto`)와 버튼 `white-space: nowrap`.
  고정 바가 떠 있는 동안 도크를 숨기는 규칙(§7.11)이 실제로 적용되는지 함께 확인.
- **검증**: 384/320px에서 고정 바 폭 = 화면 폭 − 24, 버튼 라벨 한 줄, 도크 비노출을 E2E로 단언. 실기기(S22+)에서 선택 핸들과 겹침 확인.

### 2. `저장` `완료` 배지가 "저장 완료"로 읽힘 — 높음

- **관찰**: 둘러보기·기록 › 저장 목록에서 북마크한 글을 끝까지 읽으면 오른쪽에 `[저장] [완료]`가 붙어 나온다.
- **근거**: 토스 라이팅 관점(`docs/26` §4.4 — 누르기 전 결과·상태 의미), 근접성(붙은 두 배지는 한 문장으로 읽힘), §1.4 진실성.
  "저장이 완료됐다(오프라인 저장?)"로 오해할 수 있다.
- **개선안**: 상태어를 겹치지 않게 — 예 `읽음`(완료 대신)과 북마크 아이콘, 또는 두 배지 사이를 넓히고 한쪽을 아이콘화.
  `DESIGN.md` §7.5의 "읽음 제목 ink-2"가 이미 있으므로 `완료` 배지 자체를 없애는 안도 검토.
- **검증**: 목록 행만 보여 주고 상태를 말하게 하는 과제(§4.4 표의 "의미 이해")로 확인.

### 3. 필터 시트가 비어 있음 — 중간

- **관찰**: 둘러보기 › 타입문넷 › 게시판 글 › 전체 게시판에서 `필터`를 누르면 제목·`초기화`·`적용`만 있는 시트.
- **원인(코드)**: `app.js openFilterSheet()`가 `catalog-controls`를 시트로 옮기지만, 이 상태에서는 형식(칩으로 나옴)·검색 대상(검색 전용)·
  작품 필터(작품 범위 전용)가 모두 숨는다.
- **근거**: Norman 시그니파이어(누를 수 있어 보이는데 할 일이 없음), Nielsen #8.
- **개선안**: 보일 필터 항목이 없으면 `필터` 버튼을 숨기거나 비활성 + 이유(`게시판을 고르면 형식 필터가 생겨요`).
- **검증**: 각 출처·범위·게시판 조합에서 필터 버튼 노출 ↔ 시트 항목 수 ≥ 1을 단위/E2E로.

### 4·5. 검색 빈 상태 — 중간

- **관찰 4**: 검색 탭을 처음 열면 `검색어를 입력하세요` 안내 아래에 `조건에 맞는 글이 없습니다.`가 같이 보인다.
  `필터`·`최신순`도 결과가 없는데 두 줄을 차지한다.
- **관찰 5**: 없는 단어를 찾으면 `0건` 아래 큰 빈 공간 뒤, 화면 아래쪽에 `결과가 없습니다. 텍스트 장서에서 찾아볼 수 있습니다.`와
  `소설에서 찾기`·`아카라이브 작품에서 찾기`가 나온다.
- **근거**: `DESIGN.md` §7.10(상태마다 다른 문장, 0을 합성하지 않음), Nielsen #1·#9, `docs/26` §2.4 #2(결과 없음 해석).
- **개선안**: 입력 전에는 결과 상태 문장을 숨김. 0건 안내는 결과 줄 바로 아래로 올리고, 검색 범위(`전체 게시판 · 제목·작성자·분류`)를
  함께 적어 "어디서 없었는지"를 알게 한다. 결과가 없을 때 정렬 컨트롤은 숨긴다.
- **검증**: 입력 전/입력 중/0건/결과 있음 4상태 캡처와 문장 단언.

### 6. 바코드 범례 근접성 — 중간

- **관찰**: `■ 읽음 ■ 읽는 중 …`이어야 하는데 `읽음 ■   읽는 중 ■` 처럼 색 칸이 앞 라벨에 붙어 보인다.
- **원인(코드)**: `barcode.js:135`가 `<i>`와 라벨 텍스트를 따로 flex 항목으로 넣어, `gap 12px`이 색 칸과 자기 라벨 사이에도 들어간다
  (`components.css:131`).
- **근거**: 게슈탈트 근접성(`docs/26` §1.3), §7.4 "요약 문장 + 범례".
- **개선안**: 범례 항목을 `<span><i></i>읽음</span>` 단위로 묶는다.

### 7·8·9. 작품 화면 일관성 — 중간/낮음

- **7 단위**: 타입문넷 작품 머리 `40편 · 읽음 1/40`, 바로 아래 바코드 요약 `40화 중 1화 읽음`.
- **8 구조**: 타입문넷 작품 = `‹ 작품 목록` + 큰 표지 + 주행동 `1편부터 이어 읽기`(primary) + `몇 편?`.
  소설 작품 = 출처 전환 줄 유지 + `← 작품 목록` + 작은 표지 + 주행동 버튼 없음 + 목록 첫 행 `처음부터 읽기 · 1화`.
- **9 가름끈**: 소설 작품의 `처음부터 읽기 · 1화` 행이 ribbon 레일+배경 — `DESIGN.md` §1.3은 ribbon을 "내 자리"에만 쓴다.
- **근거**: 야콥·Nielsen #4(같은 종류 화면은 같은 구조), §1.3 기억점, §1.5 표현 강도(작품 상세 = 높음).
- **개선안**: 작품 화면 머리를 하나의 구조로(뒤로 표시·표지 크기·주행동 위치). 주행동은 `이어 읽기 · N화`/`처음부터 읽기` 중 하나를
  primary 버튼으로, 회차 목록 행은 현재 자리만 ribbon. 단위는 출처 관례(편/화) 하나로 통일.

### 10. 둘러보기 머리 높이 — 중간(설계 검토 필요)

- **관찰**: 384×800에서 앱 바(56) + 출처 4분할 + 범위 탭 + 게시판 도크 + 형식 칩/필터 + 결과 줄 = 목록 시작이 y≈290(약 45%).
  첫 화면에 글 3.5개. 스크롤하면 접히므로 계속 읽을 때 비용은 작다.
- **근거**: 힉·인지 부하(결정 지점의 선택지), `DESIGN.md` §4.2(위쪽 15%는 표시 전용 + 드문 행동) — 게시판 바꾸기·필터·정렬이
  화면 위 절반에 있다.
- **제안(검토)**: 결과 줄(`40건 · 최신순`)과 칩 줄 합치기, 또는 출처 전환을 게시판 시트 안으로. 실제 사용 빈도(출처 전환 vs 게시판 바꾸기)를
  먼저 확인한 뒤 결정. 확정 설계(§4.3 폰 목록 머리)를 바꾸는 사항이라 사용자 결정 필요.

### 11·12. 더보기 시트 구획과 `저장` 용어 — 중간(검토)

- **11**: 13개 타일이 한 격자. `DESIGN.md` §8.3은 `이 화 · 보기 · 작품 · 기기` 네 구획. 그룹 제목이 없어 `작품 목차`와 `본문 찾기`,
  `작품에서 찾기`가 같은 층위로 섞인다. 개선: 구획 제목 4개(청킹), 자주 쓰는 순서(본문 찾기·저장·메모)를 앞에.
- **12**: 상단 바 북마크 아이콘·더보기 `저장`·목록 배지 `저장`은 "다시 볼 글로 표시"이고, 설계의 `이 기기에 저장`은 "연결 없이 읽기"다.
  `docs/26` §6.2 D·§4.4가 지적한 개념 충돌. 개선 후보: 북마크 쪽을 `보관함에 담기`/`책갈피`처럼 다른 동사로.
  용어 변경은 기록 화면·백업 문구까지 걸리므로 결정 후 일괄 변경.

### 13·14. 서재 화면 — 낮음

- **13**: 읽던 작품 표지 아래 `1/40편 · 이어 읽기`. 실제로는 "40편 중 1편을 끝까지 읽음"이다. 미니바는 같은 시점에 `5편 제목`.
  개선: `1편 읽음 / 40편` 또는 바코드 미니와 함께, `이어 읽기` 대상 회차 표기(`5편부터`).
- **14**: 스마트 서재 칩 아래 빈 공간이 커서 다음 모듈과의 관계가 끊겨 보임(근접성). 읽은 기록이 없을 때 `10화 이하 1` 같은
  조건 칩은 온보딩과 경쟁(§9 "기록이 없으면 온보딩 한 블록").

### 15. 통계 실패 문구 — 낮음

- `ownerIdentity()`(`/api/v1/me`)가 계정 해시를 못 받으면 저장소를 열지 않고 `이 기기에서 기록 저장소를 열 수 없습니다`.
  원인이 기기가 아니라 로그인 식별일 때도 같은 문장이다. 운영(Access 로그인)에서는 보통 발생하지 않는다.
- 개선: 원인별 문장 — `로그인 정보를 확인하지 못했어요 · 다시 시도` / `이 브라우저가 저장소를 막았어요(비공개 모드 등)`.
  같은 탭에서 쓸모없는 `제목, 메모, 태그 검색` 입력칸도 통계 보기에서는 숨긴다.

## 3. 흐름(동작 순서) 점검

| 흐름 | 결과 |
|---|---|
| 서재 → 둘러보기 → 글 열기 → 읽기 → 목록 복귀 | 통과. 복귀 시 스크롤 위치·읽은 행 상태 유지 |
| Reader `다음 편` (연재 38/40) | 통과. 39편으로 이동, 기록은 38·39만 생김 |
| 미니바 1탭 → 이어 읽기 | 통과. 마지막 연 글로 바로 진입 |
| Reader 찾기 → 닫기 | 통과. 적중 수·위치 띠·좁은 폭 2줄 |
| 문장 선택 → 메모 | **실패 위험**(§2 #1 고정 바) |
| 검색 진입 → 0건 → 다른 출처로 넓히기 | 동작은 하나 안내 위치·중복 문장(§2 #4·5) |
| 작품 화면 → 이어 읽기 | 타입문넷은 primary 버튼, 소설은 목록 첫 행 — 경로가 출처마다 다름(§2 #8) |

## 4. 재현되지 않아 제외한 의심

- "38편에서 `다음 편`이 37편으로 감", "열지 않은 36편이 `처음만 봄`": 첫 실행에서 점검 스크립트의 화면 탭이
  목록 행을 누른 결과였다. 두 번째 실행에서 `다음 편` → 39편, 기록 38·39만 확인.
- AA 화면의 한 줄짜리 그림: fixture의 줄바꿈 처리 문제로 보이며 실제 AA 판정에 쓰지 않았다.

## 5. 미검증(이 점검으로 판정하지 않은 것)

- **통계·오늘의 발췌·이번 주 기록**: 로컬에 Access 계정 식별이 없어 기록 저장소가 열리지 않음 → 운영 로그인 환경에서 재점검 필요.
- **실기기**: OS 선택 핸들·키보드 위 찾기 바·제스처 Back·safe-area·120Hz는 S22+ 실기기 확인 필요(`DESIGN.md` §11).
- **다크 테마·Reader 테마(종이·먹)·반투명 끄기**, **키보드만 사용**, **스크린리더**, **오프라인 저장(G9)**, **AA 실제 원문**,
  **아카라이브 작품별·수동 문서**: 이번 경로에 포함하지 않음.
- 사용자 과제 관찰(`docs/26` §4.4)은 하지 않았다. 위 판정은 화면·코드 근거이며 "사용하기 쉬움"의 판정이 아니다.
